2. 详解：从选框架到评测方法架构

按视频文档的 2.1–2.6 顺序展开；每节先给【视频原述】，再给【补充】，图示全部为矢量重绘。

2.1 选框架：EvalScope + MTEB + RAGAS

视频原述「框架选型的思路是：用 EvalScope 做统一调度，底层用 MTEB 和 RAGAS 分别负责检索评测和生成评测。」

图 2｜RAG 评测框架（视频 2.1 节核心架构图，节点文字与配色逐字还原）
框架视频给出的定位评测对象判分方式代表指标 / 输出
EvalScope统一调度器；阿里魔搭（ModelScope）出的评测调度框架；负责统一编排、统一结果格式、统一可视化（Dashboard），自身不实现任何指标。类比「考试组织方」——不命题、不批卷，只负责安排考什么、汇总成绩整个评测流程不判分，只编排Dashboard、统一结果格式
MTEB检索评测框架；全称 Massive Text Embedding Benchmark（大规模文本嵌入基准）检索 / embedding 层人工标注 qrels 判分Recall@K、Precision@K、NDCG@K、MRR、HitRate@K
RAGAS生成评测框架；全称 Retrieval Augmented Generation Assessment生成层（及上下文质量）LLM as a Judge 判分Faithfulness、AnswerRelevancy、ContextPrecision、ContextRecall、AnswerCorrectness

补充 · 官方口径校准视频把 EvalScope 概括为「不实现任何指标的调度器」，在本视频的 RAG 评测链路语境下是准确的；但从框架全局看需要补一句：EvalScope 是魔搭社区官方的模型评测与性能基准框架，其 RAGEval 后端确实支持「用 MTEB/CMTEB 独立评测 embedding 与 reranker 模型 + 用 RAGAS 做端到端 RAG 评测」；同时它还有 Native / OpenCompass / VLMEvalKit 等评测后端，内置 MMLU、CMMLU、C-Eval、GSM8K 等基准与相应指标。也就是说「自身不实现指标」指的是在 RAG 评测这条链路里它不做判分，而非框架整体没有指标实现。

补充 · 三者并非同一层级MTEB 原是面向文本嵌入模型的大规模基准（检索、重排、分类、聚类、STS 等任务），检索任务沿用 BEIR 风格的 corpus / queries / qrels 三件套，主指标常用 NDCG@10；RAGAS 是面向 RAG 流水线输出的指标库，多数指标以 LLM 作裁判。把两者接到同一调度层下，是视频这套体系的工程价值。

2.2 设计 baselines：横向方案 × 纵向参数

视频原述「从两个正交维度设计 baseline」：

  • 横向 · 方案结构：变方案 → 产生新 baseline（比如 纯向量 / 向量 + BM25 / 向量 + BM25 + 重排）。
  • 纵向 · 参数取值：变参数 → 属于同一 baseline 的 parameter sweep（比如 top_k、rerank_top_n）。
  • 「两个维度正交组合 → 实验矩阵（每格一次完整 RAG 跑 + 评测），矩阵总格数 = 各条 baseline 的 sweep 次数之和（Σ）。」
图 3｜实验矩阵：横向方案结构 × 纵向参数取值（按视频「实验设计」图还原：top_k=3 行以黄色虚线框标出、本行不写「运行」，第三列为注释框；图下方黄色公式条给出总运行次数）

视频原述图中 top_k=3 这一行不写「运行」：前两列区域是一个黄色虚线框（框内留白），第三列位置另放白色注释框「← 我们这次实际只做了这一行」，箭头指向黄色框；top_k=1 与 top_k=5 两行的三格均为「运行」。矩阵下方黄色公式条：总运行次数 = Σ n_i（每条 baseline × 该 baseline 的 sweep 次数），其中 Σ = baseline 条数、n_i = 第 i 条 baseline 的 sweep 次数。

维度变的是什么产出回答问题视频中的例子
横向：baseline 对比方案结构（加减模块）3–5 条候选方案，粒度粗「某个优化有没有用」→ 决定用不用纯向量 / 向量+BM25 / 向量+BM25+重排
纵向：parameter sweep参数取值（调旋钮）每个方案一条曲线，粒度细「最优参数值 / 拐点」→ 决定设多少top_k ∈ {1,3,5,10}、rerank_top_n ∈ {1,3,5}

视频原述最佳实践顺序（文档同页小字）：「先横向对照（决定用不用某模块），再纵向 sweep（决定参数取多少）」。

补充这本质是消融实验（ablation） + 超参搜索的组合：横向每加一个模块都在做控制变量，纵向是网格搜索（grid search）；参数多时改用随机搜索 / 贝叶斯优化更省算力。实验必须固定随机种子、语料版本、judge 模型与 prompt 版本，否则「指标提升」可能只是噪声；样本量小时建议用配对比较 + 显著性检验（如 bootstrap 置信区间），而不是直接比两位小数。

指标算法一句话含义
Recall@K命中的相关文档数 / 全部相关文档数相关文档找全了没有
Precision@K命中的相关文档数 / 返回的 K 个返回的结果准不准（掺没掺噪声）

MRR1 / 第一个相关文档在实际检索结果里的排名第一个对的结果排得靠不靠前

视频补充说明：「其中 NDCG 的 DCG 用 Σ(2^rel − 1) / log₂(位置+1)，IDCG 是『把相关文档排到最前』的理想 DCG。」

补充 · 公式写严谨设位置 i 上文档的相关度等级为 rel_i，则 DCG@K = Σ_{i=1..K} (2^{rel_i} − 1) / log₂(i + 1)；IDCG@K 是把所有文档按 rel 降序排列后算出的 DCG；NDCG@K = DCG@K / IDCG@K，取值 0–1。MRR = (1/|Q|)·Σ_q 1/rank_q。注意 rel 可以是多级（视频示例用 rel2 / rel1），这正是 NDCG 比 HitRate 更细的原因。

ContextRecall① 把标准答案拆句 → ② LLM 逐句判「能否归因于上下文」被覆盖句数 / 标准答案总句数

补充 · 版本口径上表是 RAGAS 0.2.x 时代 AnswerCorrectness 的典型权重（事实 F1 : 语义相似度 = 0.75 : 0.25）；新版本已将事实正确性拆为 FactualCorrectness、把语义相似度拆为 SemanticSimilarity，并新增 NonLLMContextPrecisionWithReference 等免 LLM 变体、以及 Agent 相关指标（ToolCallAccuracy、AgentGoalAccuracy 等）。写评测代码时请锁定 RAGAS 版本，否则同一份数据跨版本分数不可比。

2.5.5 联系：两套指标其实有重叠

视频原述「两部分指标不是绝对分割，而是有重合的。最明显的重合：ContextPrecision / ContextRecall vs MTEB 的 Precision / Recall——都在衡量『召回得对不对』，只是思想不同」：

对比项MTEB 的 Precision / RecallRAGAS 的 ContextPrecision / ContextRecall

参照物文档 ID 标注标准答案（自然语言）
视角检索器视角生成器视角

所以指标按评测对象可再归位：

  • 评检索：MTEB 全部 + RAGAS 的 Context 系列（后者本质也在评检索，只是换成 LLM 判）。
  • 评生成：RAGAS 其余三个（Faithfulness / AnswerRelevancy / AnswerCorrectness）。
这个「归位」是视频最有价值的方法论之一：不要按框架名归类指标，要按被评测对象归类指标。RAGAS 名字里有 Generation，但它的两个 Context 指标测的其实是检索质量。

3. 上线与迭代：从评测到上线的一个闭环

检索 / 生成两层RAG 的两段流水线；视频全部评测设计的出发点就是「两层分别测」。

Precision@K前 K 条中命中的相关文档数 / K；「返回里掺了多少噪声」。
HitRate@K前 K 条里是否至少有一个相关文档（0/1），对多跳问题过宽松。
MRRMean Reciprocal Rank，第一个相关文档排名倒数的均值；关注「第一条对不对」。

DCG / IDCGDCG = Σ(2^rel−1)/log₂(i+1)；IDCG 是把相关文档按 rel 降序排列后的 DCG。
Faithfulness / 忠实度答案中的每个事实是否都能由检索上下文推出；对应「幻觉」检测，但不等于答案正确（上下文本身可能错）。
Groundedness / 有据性与 Faithfulness 近义，TruLens 的 RAG Triad 之一，强调回答有据可查。
AnswerRelevancy答案是否切题；RAGAS 的经典做法是从答案反推「假想问题」，再算与原问题的余弦相似度。
ContextPrecision / ContextRecall上下文精确率（相关片段是否排在前面）/ 上下文召回率（标准答案中的句子能否归因到上下文）；本质是检索层指标。
AnswerCorrectness答案相对标准答案的事实正确性；视频公式为 0.75×事实F1 + 0.25×语义相似度。
事实 F1 / TP·FP·FN把答案与标准答案拆成原子事实，按真阳性 / 假阳性 / 假阴性算 F1。
LLM-as-a-Judge用大模型按评分细则当裁判；可规模化，但存在裁判偏见、位置/长度偏见与 prompt 敏感。
BLEU / ROUGE基于 n-gram 重叠的传统生成指标；对「换个说法但正确」的答案不友好，只适合字面相似场景。
余弦相似度 / 语义相似度用 embedding 向量夹角衡量语义接近程度；常用于 AnswerRelevancy 与答案相似度。
Exact Match（精确匹配）字符串 / 正则 / 结构化字段完全一致才通过；最便宜也最死板，适合 JSON 字段、拒答标记断言。
EvalScope魔搭社区官方模型评测与性能基准框架；RAGEval 后端串联 MTEB/CMTEB 与 RAGAS，本视频中作「统一调度器」。
MTEB / CMTEB / BEIRMassive Text Embedding Benchmark（大规模文本嵌入基准）/ 中文版 / 检索评测数据集格式与基准的常用来源。
RAGASRetrieval Augmented Generation Assessment；面向 RAG 的指标库，多数指标用 LLM 做局部判断再确定性聚合。
Dashboard统一结果可视化面板；视频中 EvalScope 的三大职责之一。
A/B 测试 / 灰度发布小比例真实流量对比新旧版本；灰度按比例逐步放量。
影子流量（shadow traffic）复制线上请求打给新版本但「只记不答」，用于零风险离线对比。
回滚（rollback）指标触发红线时切回上一版本；需预先定义红线与自动化开关。
数据飞轮bad case 回流 → 补进评测集 → 门槛更严 → 下一轮更准的正循环。
bad case线上真实失败样本；比人工构造的送分题更有价值。
query 漂移 / 数据漂移线上问题分布随时间变化（新词、新类目、新问法），会让离线评测集失效。
P95 延迟 / Token 成本95 分位响应耗时、单次请求的大模型 Token 开销；属于「系统层」主指标，也是上线门槛的一部分。

门禁阈值怎么写

  • 分层设阈值，不用单一加权总分：例如 NDCG@10 ≥ 0.80、Recall@10 ≥ 0.90、Faithfulness ≥ 0.90、AnswerCorrectness ≥ 0.80、P95 ≤ 2s、拒答正确率 ≥ 0.95。
  • 相对上一版：优化项需显著改善，其余指标下降不超过容差（视频给的是 ±2%）。
  • 红线一票否决：视频红线是「延迟不超预算」；工程上还常把幻觉、越权、敏感信息泄露、超时一并列入。
  • 保留逐 query 明细：视频强调「整批平均」才可比可复现，但排障必须能下钻到单条样本。

② 纯 Python 实现视频的 5 个检索指标（可复现 0.906 / 0.640 / 0.773）

import math
from collections import defaultdict

def dcg(gains):
    return sum((2 ** rel - 1) / math.log2(i + 2) for i, rel in enumerate(gains))

def evaluate_one(ranked, qrel):
    """ranked: 实际排名得到的 doc id 列表; qrel: {doc_id: 相关度等级}"""
    k = len(ranked)
    gains = [qrel.get(d, 0) for d in ranked]
    relevant = {d for d, r in qrel.items() if r > 0}
    hits = sum(1 for d in ranked if d in relevant)
    first = next((i for i, d in enumerate(ranked, 1) if d in relevant), None)
    ideal = sorted((r for r in qrel.values() if r > 0), reverse=True)
    idcg = dcg(ideal[:k]) or 1.0
    return {
        f"Recall@{k}":    hits / len(relevant),
        f"Precision@{k}": hits / k,
        f"HitRate@{k}":   1.0 if hits > 0 else 0.0,
        "MRR":            1.0 / first if first else 0.0,
        f"NDCG@{k}":      dcg(gains) / idcg,
    }

cases = [
    # Query 1：视频示例，K=5
    (["doc3", "doc7", "doc1", "doc9", "doc2"], {"doc1": 2, "doc2": 1, "doc3": 2}),
    # Query 2：视频示例，K=4
    (["doc8", "doc5", "doc2", "doc6"], {"doc5": 2, "doc6": 1}),
]
results = [evaluate_one(*c) for c in cases]
for i, r in enumerate(results, 1):
    print("Query", i, {k: round(v, 3) for k, v in r.items()})

# 整个数据集得分 = 所有 query 的算术平均（视频 5 张黄色卡片）
keys = ["Recall", "Precision", "HitRate", "MRR", "NDCG"]
for key in keys:
    vals = [next(v for k, v in r.items() if k.startswith(key)) for r in results]
    print(key, "平均 =", round(sum(vals) / len(vals), 3))
# 输出：Recall 1.000 / Precision 0.550 / HitRate 1.000 / MRR 0.750 / NDCG 0.773

4.5 常见误区与 Agent 评测衔接

误区正确做法
只看一个「答案准确率」检索层与生成层分开测，才能归因到该换 embedding 还是该改 prompt
用 reference 倒推 retrieved_contexts必须回填真实跑出来的 contexts，否则 Faithfulness / ContextRecall 虚高
测试集全是「一问一答」送分题补多跳、不可回答、冲突、口语、权限等题型
换 judge 模型 / prompt / embedding 后直接比分数锁定版本，或在同一次实验里跑完所有 baseline
只看平均分保留逐 query 明细，重点看低分样本与长尾
把 RAGAS 的 Context 系列当「生成指标」按评测对象归位：Context 系列本质是检索指标
Faithfulness 高就认为答案正确还要看 AnswerCorrectness；上下文本身可能过期或错误
离线分数漂亮就直接全量上线灰度 + 影子流量 + 线上监控 + 红线回滚
评测集一次建好不再维护bad case 回流、定期去噪、监控 query 漂移
用同厂商模型当裁判且不校准换不同模型族做 judge，定期人工抽检算一致性
忽略延迟 / Token 成本系统层与质量层一起设门槛，看 P95 而非均值

与 Agent 评测的衔接：本视频是「Agent」合集第 20 集，紧邻的第 21 集是《5min 带你搞懂 Agent 评测体系》。RAG 指标回答的是「说得好不好」，Agent 评测还要回答「做得对不对、省不省」：

层次关注对象典型指标
RAG 层（本视频）检索片段 + 生成答案Recall / NDCG / Faithfulness / AnswerCorrectness 等
Agent 层（延伸）完整执行轨迹（Trace / Span）任务完成度、规划合理性、工具选择与参数正确性、步骤效率、循环/重试检测、多轮主题一致性

两者互补：Agent 内部往往包含 RAG 检索这一步，应在对应 span 上挂 RAG 指标，在整条 trace 上挂 Agent 指标，分开采集、分开告警，避免故障归因混乱。
