2. 先说结论：三个抽象层次，不是三个竞品

图 2｜三个抽象层次重绘

视频原述口播：「LangChain 主要解决 Agent 基础组件和工具集成问题；LangGraph 主要解决 Agent 流程编排和状态管理问题；Deep Agents 则是在这些基础能力之上，进一步封装了任务规划、上下文管理、子智能体等能力，让 Agent 能够处理更加复杂、更加长期的任务」。

可以把它们理解为三个不同抽象层次的开发框架，而不是三个完全平行、彼此竞争的产品。

补充这与本站《Agent 开发架构选型 · 完全教程》里 Framework → Runtime → Harness 的三层抽象完全对应：LangChain 是框架层，LangGraph 是运行时层，Deep Agents 是 Harness 层。第四篇讲七个代表项目的横向对比，本篇只讲 LangChain 自家这三层怎么选、怎么联用。

3. LangChain 的起点：一个企业智能客服

图 3｜智能客服场景与手写痛点重绘

视频原述视频给的第一个例子是企业智能客服：系统需要查询企业知识库，或者调用订单接口，最后把查询结果整理成自然语言返回给用户。口播强调「这种场景其实就是一个比较典型 Agent 应用」。

视频原述如果从头写，要自己解决四件事：怎么接入大模型、怎么定义工具、怎么让模型调用工具、模型和工具之间如何传递消息——「开发工作会比较繁琐」。

3.1 从零搭建的四项工作

  1. 模型接入：对接不同厂商的推理接口与参数。
  2. 工具定义：把知识库检索、订单查询等能力描述成模型可调用的函数。
  3. 工具调用：解析模型输出、发起调用、处理返回。
  4. 消息传递：维护模型与工具之间的多轮消息序列。

4. LangChain 的基础组件与 create_agent

图 4｜LangChain 基础组件重绘

视频原述画面列出 LangChain 提供的基础组件：模型接入、Prompt、消息管理、工具调用、文档加载、向量数据库、检索器；口播原话是「开发者可以直接使用这些组件，快速搭建一个 Agent 应用」。

图 5｜create_agent 与工具循环重绘

4.1 create_agent：准备好三样东西

视频原述「LangChain 提供了 create_agent 这样的高层接口。开发者只需要准备好大模型、工具和系统提示词，就可以创建一个能够调用工具的 Agent。」

4.2 模型—工具循环

视频原述执行过程：大模型分析当前任务 → 判断是否需要调用工具 → 需要就选择合适工具执行并返回 → 大模型再根据工具结果继续处理。这个循环的调度由框架接管，开发者不必手写状态机。

官方文档补充：LangChain 1.0 的 create_agent 构建在 LangGraph 运行时之上，但「你不需要了解 LangGraph 就能用 LangChain」。这是「层层叠加」而非「必须同时使用」的直接证据。

5. 由模型按当前问题选择工具，以及适用场景

图 6｜按问题选工具与适用场景重绘

视频原述画面给出两个并列例子：「用户询问企业某项业务制度 → 调用知识库检索工具」「用户想查询订单状态 → 调用订单查询接口」，并标注「由模型根据当前问题进行判断」。

视频原述适用场景：企业知识库问答、RAG 应用、智能客服，以及需要调用数据库或第三方 API 的智能助手。口播总结：「这些应用通常不需要特别复杂的流程控制，主要依靠大模型判断下一步应该做什么」。

场景典型动作为什么 LangChain 够用
企业知识库助手检索 → 生成回答以问答与工具调用为主
RAG 应用文档加载 / 向量库 / 检索器基础组件已内置
智能客服按问题选知识库或订单接口由模型判断下一步
简单数据查询助手调用数据库 / 第三方 API无需复杂流程编排

6. 中间件扩展与 LangGraph 的引出

图 7｜中间件扩展与 LangGraph 引出重绘

视频原述口播特意补了一句：「LangChain 并不只能开发简单应用，它也支持通过中间件等方式扩展 Agent 执行过程」。画面列出四类扩展：条件分支、状态转换、异常重试、人工审批。

但当「出现大量条件分支、状态转换、异常重试和人工审批」时，流程就不再适合全部交给模型判断——这正是 LangGraph 的主场。

补充注意这是抽象层次下移，不是产品淘汰：从「让模型判断下一步」变成「让开发者定义下一步」。

7. LangGraph 的起点：企业售后处理系统

图 8｜售后流程与业务规则重绘

视频原述第二个例子是企业售后处理系统：先识别问题类型，然后查询订单，接着进行风险校验；符合就进入退款审批，不符合就转入其他处理流程。

视频原述口播强调：「不能完全交给大模型决定」「什么时候必须进行风险校验，什么时候需要等待人工审批」——这些是明确的业务规则，不是模型的自由裁量。

画面小节导航依次为「LangGraph•售后处理流程」「LangGraph•明确业务规则」「LangGraph•图的三个要素」「LangGraph • State 共享状态」「LangGraph・Node 执行任务」「LangGraph • Edge 条件流转」「LangGraph•精确控制执行」。

8. 图三要素：State / Node / Edge

图 9｜图三要素重绘

视频原述「LangGraph 使用图结构来组织整个执行流程」，三个概念：State（状态，保存工作流执行过程中需要共享的数据）、Node（节点，例如调用大模型识别问题类型、查询订单信息、执行风险校验）、Edge（定义节点之间的流转关系）。

图 10｜三要素落地重绘

8.1 三要素落到售后例

要素画面原文售后系统里的具体值
State共享数据用户提交的退款申请、订单信息、风险校验结果
Node具体任务识别问题类型、查询订单信息、执行风险校验
Edge流转关系风险校验通过 → 退款审批；未通过 → 异常处理

视频原述「一个节点执行一个具体任务」「根据条件决定下一步执行哪个节点」，于是整个售后流程被拆成多个节点，开发者能明确控制每个环节的执行顺序。

9. 条件流转与精确控制

图 11｜条件流转与精确控制重绘

视频原述画面用「风险校验 → 通过 / 未通过 → 退款审批 / 异常处理」演示条件边。核心价值口播原话：「它让开发者能够更加精确地控制 Agent 的执行过程」。

LangGraph 的价值不在于「让 Agent 更聪明」，而在于「让流程更可控」——把确定性环节固定下来，把需要判断的环节留给模型。

10. 暂停、恢复与生产级能力

图 12｜暂停与恢复重绘

视频原述「除此之外，LangGraph 还提供了持久化检查点、流式输出、执行中断和人工介入等能力」。例子：退款流程执行到人工审批环节，系统先暂停运行，等人工审批完成后，再从之前暂停的位置继续执行；任务异常时也可结合检查点保存的状态恢复执行。

能力画面文字解决什么
持久化检查点检查点保存状态 → 恢复执行长时间运行 / 故障恢复
流式输出流式输出过程可见、逐步返回
执行中断暂停等待在关键节点停下来
人工介入人工确认 → 继续执行审批与人工把关

11. 适用场景与「代码 + 模型」分工

图 13｜适用场景与分工重绘

视频原述适用场景：多步骤业务流程、复杂条件分支、循环重试、人工审批，以及需要保存状态并支持中断恢复的 Agent 系统；典型如订单处理、退款审批、企业工单系统。

视频原述视频特意强调：「LangGraph 并不意味着所有步骤都必须交给大模型处理。相反，它非常适合把确定性的业务逻辑交给普通代码，把需要理解和判断的任务交给大模型」。

判断标准：这一步的结果是否只能由语义理解得出？不是，就写普通代码；是，才交给模型。

12. Deep Agents：只给目标，由 Agent 自己规划

图 14｜Deep Agents 定位与代码修复任务重绘

视频原述第三个例子：给 AI 一个任务「分析当前项目的代码仓库，找出登录模块存在的问题，修复相关代码，然后运行测试」——「注意，这个任务并没有规定具体应该执行哪些步骤」。

视频原述Agent 需要自己理解目标、分析代码仓库、找到相关文件、制定修复计划、修改代码、运行测试；「测试失败 → 分析错误 → 调整代码」，直到达到预期结果。整个过程涉及大量文件和工具调用，还需要保存中间发现的信息。

视频原述「如果这些功能全部由开发者自己实现，工作量较大」，而 Deep Agents 就是为这类复杂任务提供更完整的执行框架。

13. 完整执行框架：建立在前两者之上

图 15｜完整执行框架重绘

视频原述画面给出一张堆叠图：底层是「LangChain + LangGraph 相关能力」，上层是「规划 / 上下文 / 文件系统 / 子智能体」，顶部标注「自行实现：工作量较大」。口播：「它建立在 LangChain 和 LangGraph 的相关能力之上，进一步整合了任务规划、上下文管理、文件系统和子智能体等能力」。

层内容来源
底层模型 / 工具组件 + 持久执行 / 状态管理LangChain + LangGraph
上层规划、上下文、文件系统、子智能体Deep Agents 封装
可选Skills、长期记忆、人工介入、沙箱与执行工具按配置启用

14. 任务规划与子智能体协作

图 16｜任务规划与子智能体重绘

14.1 任务规划：大目标 → 可跟踪的具体步骤

视频原述「Agent 可以把任务拆分成多个具体步骤，并跟踪每个步骤执行情况」。代码修复任务可拆成代码分析、问题定位、代码修改、测试验证、结果整理。

14.2 子智能体：把独立子任务交给专门 Agent

视频原述主 Agent 负责整体任务规划；一个子 Agent 分析代码结构，另一个子 Agent 检查测试结果；完成后「子任务结果返回 → 主 Agent 汇总处理」。

官方文档补充：规划工具 write_todos 在新版为可选中间件（TodoListMiddleware）；子智能体通过内置 task 工具创建，默认隔离上下文并只返回一份最终结果。

15. 文件系统与上下文管理

图 17｜文件系统与上下文管理重绘

视频原述「在复杂任务中，Agent 可能需要读取大量文件，也可能需要把中间结果保存下来」。Deep Agents 提供文件系统能力，通过文件读写保存研究资料、任务计划和中间产物，「减少所有信息都堆积在对话上下文中的情况」。

视频原述口播点出根因：「Agent 执行时间越长，调用工具越多，对话历史和工具返回结果就可能越来越多」，所以需要「通过摘要、文件卸载等方式控制上下文规模」。

机制画面文字作用
文件读写研究资料 / 任务计划 / 中间产物把大结果移出对话
摘要摘要压缩历史对话
文件卸载文件卸载卸载大工具结果
Skills可复用知识与流程按需加载领域知识
长期记忆按配置使用跨会话保留偏好

16. 可扩展能力、适用场景与权限边界

图 18｜可扩展能力与权限边界重绘

20. 三者能否一起用：可以，按项目需求组合

图 22｜三者联用重绘

视频原述「答案是可以，而且它们之间本身就存在比较紧密的技术联系」：LangChain 提供模型、工具和 Agent 等基础组件；LangGraph 提供底层状态管理和流程编排；Deep Agents 在前两者之上封装任务规划、上下文管理和子智能体。

视频原述具体组合方式：「我们可以在 LangGraph 的节点中调用 LangChain 提供的模型和工具，也可以使用 Deep Agents 提供的任务规划和子智能体能力，再根据实际业务需求进行定制」。画面还标注「LangGraph 可以独立使用」。

21. 总结：让框架服务于业务

图 23｜总结选型矩阵重绘

视频原述口播收束：简单知识库助手或能调用几个工具的智能客服 → LangChain；有明确业务流程、复杂条件分支和人工审批 → LangGraph；希望 Agent 自主规划、管理上下文、调用多个工具甚至安排子智能体协作完成长期任务 → Deep Agents。

「实际开发中，建议从满足当前需求最简单方案开始，不要一上来就引入过多框架和复杂架构。真正合适的技术选型，是让框架服务于业务。」

24.2 用状态机模拟 State / Node / Edge

from dataclasses import dataclass, field


@dataclass
class State:
    question: str = ""
    problem_type: str = ""
    order: dict = field(default_factory=dict)
    risk_ok: bool = False
    result: str = ""


def identify(s):
    s.problem_type = "refund"
    return s


def query_order(s):
    s.order = {"id": "A100", "amount": 199}
    return s


def risk_check(s):
    s.risk_ok = s.order["amount"] < 500
    return s


def edge(s):
    return "退款审批" if s.risk_ok else "异常处理"


nodes = {"问题识别": identify, "查询订单": query_order, "风险校验": risk_check}
s = State(question="我要退款")
for name, fn in nodes.items():
    s = fn(s)
    print(f"Node {name}: {s}")
print("Edge 下一节点:", edge(s))

24.4 上下文规模控制（摘要与文件卸载）

import json
from pathlib import Path


def offload(history, tool_results, threshold=120):
    """把大工具结果写到文件，只在上下文里保留摘要与路径。"""
    context, offloaded = [], []
    for item in history + tool_results:
        if len(item) > threshold:
            path = Path(f"artifact_{len(offloaded) + 1}.txt")
            path.write_text(item, encoding="utf-8")
            offloaded.append(str(path))
            context.append(f"[已卸载 → {path}] {item[:24]}...")
        else:
            context.append(item)
    return context, offloaded


history = ["用户：修复登录模块", "Agent：开始分析仓库"]
results = ["工具返回：" + ("登录流程日志 " * 20), "工具返回：OK"]
ctx, files = offload(history, results)
print("上下文:", json.dumps(ctx, ensure_ascii=False, indent=1))
print("卸载到文件:", files)
for f in files:
    Path(f).unlink()

25. 补充篇 D：常见误区

#误区为什么错正确做法
1把三者当成互相竞争的同类产品它们是三个抽象层次，层层叠加按需要的抽象层次选起点
2认为用 Deep Agents 就必须同时装三个框架Deep Agents 已封装下层能力按项目需求决定，LangGraph 也可独立使用
3用 LangChain 硬写大量条件分支与人工审批流程控制不是它的主场流程复杂时下移到 LangGraph
4用 LangGraph 就每一步都调大模型确定性逻辑用普通代码更可控代码管确定性，模型管理解与判断
5简单知识库问答直接上 Deep Agents引入了用不到的规划与子智能体从满足当前需求的最简单方案开始
6把固定报表流程做成 Agent完全固定、无需模型判断普通 Python / 传统工作流系统
7把人工审批交给模型自己决定业务规则不能靠自由裁量用条件边 + interrupt + 人工确认
8长时间任务把全部中间结果留在对话里对话历史与工具结果会撑爆上下文摘要 + 文件卸载 + 子 Agent 隔离
9子智能体共享全部主对话上下文上下文被重型子任务污染默认隔离上下文，只回传最终结果
10给 Deep Agents 无限制的文件与命令权限可能误改文件、执行命令、写库权限控制 + 沙箱隔离 + 人工审批
11以为 LangGraph 只是「流程图库」还提供持久执行、流式、HITL、恢复把它当运行时层来评估
12把 LangChain 中间件当成流程编排替代品扩展点不等于显式图结构大量分支/状态时用图
13用「哪个框架最新」做选型依据新旧不代表替代关系按三个业务问题判断
14认为 LangGraph 节点里不能调 LangChain 工具两者本就设计为可组合在节点中复用模型与工具组件
15忽略视频标题里的拼写差异直接照抄官方是 LangGraph / Deep Agents校正后按官方名检索文档
