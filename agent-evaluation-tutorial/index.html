1. 体系架构：三层分类 × 一条流程

图 1｜体系架构：三层分类 × 一条流程（按视频文档「一、体系架构」结构化重绘）

和 RAG 评测的关系：RAG 评测评的是「一问一答」，Agent 评测评的是「一条多步执行的轨迹」。所以 Agent 评测要回答三个问题——做成了没、怎么做的、代价多大，对应三层分类；而不管评哪一层，流程都是同一条五步。

正交关系：三层分类和流程是正交的——任何一次具体评测，都落在「某一层 × 某一步」的交叉点上。

这也是本集与上一集最本质的区别：RAG 评测按组件（检索 / 生成）拆，Agent 评测按结果 / 路径 / 代价拆，并且必须围绕完整 trace（执行轨迹）而非单次输入输出。

2. 详解

按文档 2.1–2.3 顺序展开；表格逐行还原，图示按文档结构重绘。

2.1 三层分类（评什么）

层官方术语评什么核心问题
①端到端评测（End-to-End）最终结果任务完成了吗
②轨迹评测（Trajectory）执行过程路径对吗、工具用对没
③表现评测（Performance）运行时指标快吗、贵吗、稳吗

视频原述「三层不是并列的三张卷子，而是一个诊断栈：先看结果有没有问题 → 结果有问题再看路径 → 路径有问题再定位到具体组件。」

图 2｜三层分类与诊断链（按视频三层分类表重绘；底部为「诊断栈」原文，定位到具体组件不属于表现评测层）

2.1.1 端到端评测

  • 是什么：把整个 Agent 当黑盒，只看输入 → 最终输出。
  • 核心指标：Task Completion（任务完成率）、答案正确性／可用性。
  • 特点：全自动、成本低；只回答「成没成」，不回答「为什么」。
  • 局限：完成率从 68% 掉到 55%，它能拉响警报，但说不清哪一步坏了。
  • 典型做法：给 Agent 一个任务，跑完看终态对不对（如 τ-bench 比对会话结束时的数据库状态与目标状态）。

2.1.2 轨迹评测

  • 是什么：评 Agent 的完整决策与行动序列——中间每一步。
  • 为什么需要：端到端只知道「没做成」，轨迹才能回答「哪一步搞砸了」。
  • 评三个方面（视频表格逐行还原）：
维度指标含义
规划Plan Quality / Plan Adherence计划合理吗 / 按计划走了吗
步骤Step Efficiency有没有绕路、无效步骤
工具调用Tool Correctness工具选对没
（同上）Argument Correctness参数传对没

2.1.3 表现评测

视频原述该层在三层分类表中给出「Performance / 运行时指标 / 快吗、贵吗、稳吗」；视频画面未滚动到 2.1.3 的独立展开段落，其具体内容由 2.2 的「Token 成本／延迟」「★ pass^k」以及 2.3 ④ 的「表现看延迟／成本／稳定」体现。

补充表现评测常见维度：P50/P95/P99 延迟、单任务 Token 与费用、工具调用次数与重试率、成功率与稳定性（pass^k）、并发下的错误率与超时率、安全事件数。它不判断答案对不对，只判断系统跑得快不快、贵不贵、稳不稳。

⚠️ 核心原则：指标是渐进的，别一上来全开。

  • 顺序：先只上 Task Completion（看总账）→ 有问题再加轨迹指标（定位哪步坏）→ 再按业务挂场景指标。
  • 依据：先做 error analysis，再决定写哪些指标（美团 / Anthropic 共识）。
  • 反例：50 个指标全开 → 成本爆炸、噪音淹没信号、没人看。

2.3 一条流程（怎么评）

视频原述「不管评哪一层，流程都是同一条：① 定数据集 → ② 定标准 → ③ 跑测试 → ④ 看指标归因 → ⑤ 持续迭代」

① 定数据集

一个用例 = 三元组：问题 ＋ 参考答案 ＋ 评价标准。按用途分三类：

② 定标准

视频原述「标准按『判得清不清』分三类，对应三种判据」：

图 6｜三种判据（按视频 2.3「定标准」表重绘）
判据适用怎么判特点
程序判断清晰的指标（工具名、参数、格式、终态状态）代码确定性断言（EQ / CONTAINS / REGEX）快、稳、可复现
大模型判断模糊的指标（答案质量、规划合理性、沟通质量）rubric（评分细则，尽量二元化：是 / 否 / 未知）懂语义，但需与人工校准
人工判断需要校准时人评结构化打分金标准，贵、慢

分工原则：能确定性就确定性——清晰的就用程序，模糊的才上 rubric，人工用来校准。

① 程序判断（清晰指标）

  • 判什么：工具名／参数／格式／环境终态。
  • 例：ToolCorrectness → 实际工具序列 == 期望序列（== 1.0 通过）。

② 大模型判断（模糊指标 → rubric）

  • 判什么：无唯一正确答案的质量维度。
  • 关键：rubric 二元化——把模糊概念拆成一组「是／否／未知」的具体检查项。
  • 例：AnswerCorrectness → rubric（0-2 错 / 3-6 大体对 / 7-9 漏细节 / 10 全对）→ 阈值 ≥ 7。
  • 前提：人机一致率达标（机器评测与人工评测一致），否则只能算「机器标注」，不算自动化评测。

③ 人工判断

  • 用途：校准前面两者，尤其校准大模型 rubric。
  • 原则：1 个「独裁者」好过 10 个「民主者」——统一口径，由一个人拍板。

③ 跑测试

按「在哪跑、有没有参考答案」分两种：

图 7｜离线评测 vs 在线评测（按视频 2.3「③ 跑测试」表重绘）
场景在哪跑有参考答案吗用途
离线评测（offline）评测集上有（reference-based）上线前回归、对比版本
在线评测（online）生产真实流量无（reference-free）发现未知问题
  • 离线的实现：跑评测集（含回放 replay——用历史 trace 重放验证新版本）。
  • 在线的实现：影子模式（上线前用真实流量兜底）、A/B（上线后确认业务价值）、巡检（日常盯基本盘）。
一句话：离线守已知，在线发现未知。

④ 看指标归因

  • 看指标：端到端看 Task Completion，轨迹看 Tool Correctness / Plan Adherence，表现看延迟／成本／稳定／安全。
  • 归因：把失败的 trace 归类成 failure taxonomy，定位「哪一层的哪一步坏了」。
  • 原则：先做 error analysis，再决定写哪些指标。

画面差异：视频前段该句写作「表现看延迟／成本／稳定」，后段画面补为「稳定/安全」；本教程取更完整的后段写法。

关键认知：离线只是门控，线上 A/B 看业务指标才是黄金标准。

⑤ 持续迭代

把线上失败的 case 回灌进评测集，形成闭环——评测集越滚越大，门槛越卡越准。

4.1 专业名词速查

名词含义
Agent能自主规划、调用工具、多步执行以完成目标的 LLM 系统；评测对象是完整执行过程而非单次问答。
Trace / Span一次完整执行轨迹 / 轨迹中的单个组件调用（LLM、工具、子 Agent）；轨迹评测必须基于 trace。
端到端评测 End-to-End把 Agent 当黑盒，只看输入 → 最终输出，回答「任务完成了吗」。
轨迹评测 Trajectory评完整决策与行动序列，回答「哪一步搞砸了」。
表现评测 Performance运行时指标：延迟、成本、稳定性、错误率，回答「快吗、贵吗、稳吗」。
Task Completion任务完成率／完成度；端到端的总账指标，常由 LLM 依据整个 trace 判定。
Plan Quality生成的计划是否逻辑合理、完整、高效（DeepEval 轨迹指标）。
Plan Adherence执行是否按自己生成的计划走；计划好却不照做是典型失败模式「计划抛弃」。
Step Efficiency是否避免了绕路与冗余步骤；与视频 2.1.2「步骤」维度对应。
Tool Correctness工具选对没；reference-based，比较实际工具序列与期望序列。
Argument Correctness工具参数传对没；常为 referenceless，由 LLM judge 结合输入判断。
pass^kτ-bench 引入：同一任务独立跑 k 次全部成功的概率，衡量可靠性；与代码生成的 pass@k（至少一次成功）相反。
τ-benchSierra 2024 的 tool-agent-user 基准：模拟用户 + 领域策略 + 工具 API，以「会话结束后的数据库终态」与目标状态比对判分。
DeepEvalPytest 风格的 LLM 评测框架，50+ 指标；Agent 侧有 6 个指标，轨迹指标需 tracing。
golden set黄金集：人工精标，定义质量下限，起步 20~50 条。
regression set回归集：历史上能做对的用例，防止版本回退，要求通过率 ≈100%。
capability set挑战集：专攻当前难题，用来标定能力边界，通过率从低起步。
用例三元组问题 ＋ 参考答案 ＋ 评价标准；视频给出的最小评测单元。
rubric评分细则；把模糊质量维度拆成可判定的检查项，尽量二元化（是／否／未知）。
二元化把连续/主观打分改造成离散断言，降低 LLM judge 的随机性与口径漂移。
人机一致率机器评测与人工评测的一致程度；未达标时机器结果只能算「机器标注」，不能称自动化评测。

⑤ pass^k：可靠性而非通过率

def pass_hat_k(runs, k):
    """runs: {task_id: [bool, ...]}，每个任务独立跑 k 次；返回全部 k 次都成功的比例"""
    ok = sum(1 for rs in runs.values() if len(rs) >= k and all(rs[:k]))
    return ok / len(runs)

runs = {"t1": [True, True, True], "t2": [True, False, True], "t3": [True, True, False]}
print("pass^1 =", pass_hat_k(runs, 1))   # 1.000
print("pass^3 =", pass_hat_k(runs, 3))   # 0.333  ← 视频强调的「稳不稳」

⑥ CI 门禁（放行标准）

GATES = {"task_completion": 0.90, "tool_correctness": 0.95,
         "argument_correctness": 0.95, "p95_latency_s": 3.0}

def release_gate(current, previous, tolerance=0.02):
    for k, threshold in GATES.items():
        v = current[k]
        if k == "p95_latency_s":
            assert v <= threshold, f"红线 {k} 超预算: {v}"
        else:
            assert v >= threshold, f"{k} 未达门槛: {v}"
            assert v >= previous[k] * (1 - tolerance), f"{k} 下降超容差"
    return True  # 统计显著需另做 bootstrap / 配对检验

4.5 常见误区与失败归因

误区正确做法
一上来把 50+ 指标全开先 Task Completion 看总账，再按 error analysis 渐进加指标
只看 Task Completion 就宣布「没问题」完成率相同也可能是绕路/参数错/靠运气，需轨迹指标下钻
③④ 分开看或只看其中一个Tool Correctness 与 Argument Correctness 成对看，否则等于没测
把 pass^k 当成 pass@kpass^k 要求 k 次全成（可靠性），pass@k 只要一次成功，含义相反
rubric 不做人机一致率校准先用人工打分校准，达标后才算自动化评测

评测体系架构（00:28–01:48）

但是又不完全相同，你可以认为 Agent 的评测是包含我们的 RAG。只不过我们上一期讲的更精细化。那我们现在就在这里介绍一下：首先 Agent 的评测主要分为三种：第一种叫做端到端的评测。第二种叫做这个轨迹评测。

第三种叫做表现评测，这三个评测其实是 DeepEval。这个非常出名的开源组织他们去定义的，那具体来说。端到端的评测其实就是一个黑盒评测，它不看你中间的过程，只看你最终的输出。你的任务完成得怎么样。那轨迹评测就是一个白盒评测，它不仅要看最后的结果。

它还要看你整个执行过程中，对吧，你的规划是不是合理的。你具体每一步有没有绕路，有没有无效的步骤。并且你的工具有没有选对，你的参数有没有传对。那第三个表现评测其实指的就是，我们的一些其他的非性能指标。比如说我们的这个，整个系统的一个成本延迟怎么样。

对吧，还有一个稳定性，我会看一个指标叫做 pass^k。还会看它的一些。安全性有没有越权。那讲完了这个分类和指标，我们下面来具体看一下。整个评测的流程是什么样子的，其实这个评测的流程。

数据集（01:48–02:29）

那首先，我们第一步准备数据集。那数据集其实就分为三类：第一类叫做这个黄金数据集。这里其实就是，相对于你整个系统来说。我们会人工评测出，各种各样的数据集。作为一些，最基本的最重要的功能。

那以后我们每次测试都要跑这数据集。那再带一个回归集。那回归集就是指，哦，我系统我以前的一些功能。看一些数据，防止的就是你新功能上线之后，影响了我旧的功能的一个稳定。第三个挑战集，就是说要验证，你这次修改了这部分功能。

有没有真正的实现。这就是我们三类数据集。然后每个数据集，它里面的数据都是包括一个问题。一个答案。那定完数据集之后。

评判标准（02:29–03:30）

我们现在就来定一下，我的标准，就是我们具体用哪些指标？以及我们这个标准什么样子的，这里其实主要分为三类：比较清晰的指标。我们就可以用一些程序做断言。比如说相不相等，包不包含，对吧。以及它的正则，满不满足。

那第二类是我们的模糊的指标，模糊的指标我们叫做 Rubric。什么意思呢，我们就要把这些指标。通过评分细则去把它二元化。比如说我们前面 Rubric 提过了一个准确率，这个准确率是个分。那可能是0.907，0.802。

这种数据你很难说。去程序的断言。所以说你要交给大模型，让大模型给你输出一个0到10分。就是说它把这个数据做一个转换。比如说0到2分就是错。

对吧，3到6分就是大体对。7到9分就是漏细节，10分是全对。这样的话就完成一个二元化。那除了这两个之外，我们还要做一些人工的判断。就是因为人工其实是最准的，最合理的，这个时候我们需要人工可以抽取。

或者说有问题出现的时候，可以做一个校准。这就是我们标准的定义。我们定完标准之后。

测试（03:30–04:10）

下一步我们就来看一下我们的测试。具体测试的时候其实也分两种：如果说在我们的评测集上去评测。就是一个离线评测。对吧。它主要依赖的是我们引入的一些数据，我们最终的效果，肯定还是要去跑生产的。

上线与迭代（04:11–04:48）

那我们评测完之后，我们就要上线了，对吧。那上线其实是一个数据的飞轮，要有持续的迭代。对吧，第一部分我要判断。你这个指标准不准，达到我的标准。它的误差有没有在容忍的范围内。

或者说把一些 bad case，回流进我的评测集。这样的话，可以撑起一整个数据飞轮。那这样的话，才是我们整个 Agent 的评测的，一个体系框架。对吧，我们最后来总结一下。

总结（04:49–05:41）

首先 Agent 的评测分为三类：分别是端到端轨迹表现。然后还有一条流程。第一步就是先建数据集，你要准备好你的 Golden Dataset。你的回归的数据集，包括你的挑战数据集。那第二步一定要定标准。

对吧，对一些准确的东西。你要用程序断言去做。对于一些模糊的东西，你要写成 Rubric。用大模型去把它量化。然后第三步你就要跑 Baseline。

那跑的话可以是离线跑，也可以是在线跑。那跑完之后你要看它具体的指标。然后把它归因。最后的话要把这个指标做一个持续的迭代，做一个数据飞轮。里面就包括达标、达标上线的要求，包括这个灰度发布。

包括线上系统的一个稳定性，包括你最后要不要回滚。以及你的 bad case 如何回流，这就是我们一整个评测体系的，那大家有什么问题可以在评论区跟我交流。拜拜。
