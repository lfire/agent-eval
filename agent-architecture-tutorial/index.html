2.1 第一阶段：Agent Framework（2022–2023）

视频原述「大概在 2022 年，大家就开始尝试基于大模型开发各种应用，但那个时候开发 Agent 的很多基础工作都要自己完成：怎么让模型使用外部的工具、怎么调用不同大模型、怎么接入知识库、怎么把工具执行的结果返回给模型、怎么让模型决定下一步……如果每开发一个 Agent 都要重写一遍，开发成本就太高了。」

画面列出「每个 Agent 都要自己手搓」的四件事：使用外部工具、调用不同大模型、接入知识库、结果回传给模型。于是出现了一批把基础能力封装起来的框架：LangChain、LlamaIndex、CrewAI 等，覆盖模型调用 / 工具接入 / 数据处理。

视频原述画面示例是「订单查询 Agent」：用户提问 → LLM Agent → 订单查询接口 → 返回结果 → 回答用户，代码框写着：

from langchain.agents import create_agent

agent = create_agent(
    model="claude-sonnet-4-5",
    tools=[query_order],
    system_prompt="你是订单客服…",
)

只需定义提示词、调用规则与工具，很快就能搭出基础版本。这一类框架主要解决的是「减少重复开发」：把每个 Agent 都要写一遍的基础连接工作变成可复用组件。

2.2 第二阶段：Agent Runtime（2024）

视频原述「随着 Agent 执行任务越来越复杂，仅仅把模型和工具连接起来还不够。比如我们要开发一个电商选品 Agent：读取商品信息 → 查询库存·价格·佣金 → 商品打分 → 生成选品结果。这里面的步骤很多，有些需要根据上一步的结果动态决定；如果任务执行到一半失败了，能不能接着之前的进度继续？如果某个环节需要人工确认，能不能先暂停、等用户确认之后再往下走？」

视频原述「这已经不只是模型调用 + 工具接入了，我们还需要管理整个任务的执行流程。于是在 2024 年 LangChain 推出了 LangGraph，核心就是让开发者能够更明确地控制 Agent 的执行过程。」画面列出 Runtime 要回答的四个问题：

  1. 有哪些步骤
  2. 步骤之间怎么流转
  3. 什么时候暂停（人工确认，先暂停等人确认）
  4. 出现异常怎么恢复（从断点继续，不用重来）

视频原述「Runtime 解决的是：怎么让 Agent 的执行过程可管、可控。」它在 Framework 之上补的是流程管理、状态持久化、暂停/恢复与人工介入。

2.3 第三阶段：Agent Harness（2025 起）

视频原述「第三个阶段是 Agent Harness。随着模型推理与工具调用能力不断提高，Agent 的开发方式又发生了变化：以前开发者往往需要提前把流程安排好，但现在很多任务的流程根本没办法提前规划，也不可能枚举所有情况；现在只给模型一个目标，让它自己规划步骤、调用工具、分析结果，再不断调整下一步的行动。」

画面示例是「研究一家公司的产品」：目标给定后，模型自己决定搜索资料 → 再搜一轮 → 验证关键信息 → 写代码分析数据 → 整理成报告。画面还用三个小标签对比了三种执行方式：01 直线流程、02 暂停／恢复、03 自主规划。

视频原述「模型自主性提高之后，又带来了新的工程问题」——画面给出四个具体追问：

  • Agent 连续执行到第 40 步，上下文从 184k 涨到 192k，上下文越来越长，怎么控制？
  • 文件和中间结果放哪里？
  • 何时调子 Agent？何时停？
  • 工具权限怎么管？

视频原述「于是 Agent Harness —— 围绕模型的一整套执行系统，也因此受到越来越多的关注。基础是 Agent Loop：模型的思考 → 调用工具 → 拿到结果 → 继续执行这个循环；在此之上还提供了上下文管理、规划、文件、权限这四类能力。过去这些能力都得自己手搓，现在现成的 Harness 已经帮我们做好了，我们可以直接使用这套现成的执行系统。」

图 4｜Harness 定义：基础 Agent Loop 与四类能力重绘

视频原述「当然了，Framework、Runtime、Harness 并不是简单的新技术取代旧技术：Harness 复用了 Framework 和 Runtime 的能力。LangChain 团队就是一个非常典型的例子——LangChain 主要提供开发基础组件，2024 年推出 LangGraph 做状态管理与持久化执行，2025 年又推出 Deep Agents，在前两者基础上提供一套更完整的 Harness。所以它们是随着模型能力和应用需求变化出现的不同层次的技术抽象，不是互相淘汰。」

补充这套三层划分与公开工程资料一致：Framework 给开发者定义行为、工具、路由、状态的抽象（LangChain / CrewAI / OpenAI Agents SDK）；Runtime 提供持久化执行、会话与进程生命周期、检查点与恢复（LangGraph / Temporal / Inngest）；Harness 是「一辆装配好的车」，打包了默认 system prompt、工具注册表、上下文工程、Hook 生命周期、沙箱与权限模型（Claude Code / Codex CLI / Cline）。三者回答的是不同问题，生产系统常同时使用：Framework 编排大流程，每个 Agent 在 Harness 内执行，Runtime 提供环境与状态。详见 11. 专业名词速查 与 13. 架构全景。

9. 怎么用 Harness：三个层次（用 Pi 举例）

视频原述「已经确定了要用哪个 Harness，然后呢？下载别人的代码来改？还是通过 SDK 开发？什么才是使用 Harness 的正确姿势？我认为可以把开发者需求分成三个层次。」

图 18｜三个层次与 Pi 的三种开发目标重绘
  1. 扩展现有的 Agent：已有能用的 Agent 产品，只想加功能。
  2. 开发自己的 Agent 产品：自己的界面、业务功能和用户体系，但不想从零开发 Agent Loop。
  3. 改造底层的 Harness：对现成的核心机制都不满意，希望自己修改甚至重新设计。

视频原述「这三个层次的开发目标不一样，技术能力要求也不同。我们就用 Pi 举个例子。」

9.1 层次一：Extension / Skill —— 产品还是 Pi

视频原述「假设你是一名程序员，公司在用 Pi CLI 做编程工具，希望它更符合公司开发流程：比如 + 自动检查代码规范、+ 按要求生成 PR 描述。你只需要在安装好的 Pi CLI 基础上，通过 Extension 或 Skill 加上这些功能，让它变得更符合你们自己的要求 —— 产品还是 Pi。」

9.2 层次二：Pi SDK —— 产品是你的，底层复用 Pi

视频原述「现在你打算出去创业，做自己的 AI 编程产品：界面、用户管理、任务系统、运行测试都要自己做。这个时候就可以用 Pi SDK，把 Pi 的执行能力集成到自己的应用里 —— 产品是你的，只是底层复用了 Pi Harness。」

9.3 层次三：改源码 —— 扩展接口不够用时

视频原述「假设你认为 Pi 默认的 Agent Loop 不够好，想重新设计模型如何决策、如何执行、整个任务如何循环，那就需要 fork、改它的核心源码，搭出自己的 Harness。」

视频原述「所以插件 · SDK · 源码改造是三个不同的问题：插件 / Skill 解决『如何扩展现有 Agent』；SDK 解决『复用现成的执行能力，开发自己的应用』；改源码是『现有的扩展接口无法满足需求的时候』才需要。」

视频原述「因此在做技术选型时，要先想清楚自己的开发目标：让现有 Agent 更好用 → 插件和 Skill；开发独立的 Agent 产品 → SDK；深入改造 Harness → 才需要关注源码的开放程度。」画面最后强调一句：「开发自己的 Agent 产品 ≠ 开发自己的 Harness」。
层次开发目标手段产品归属典型成本

def rank(need_default, need_control, need_scenario, cost_tolerance=5):
    """need_* 取 1..5；cost_tolerance 越低越不愿承担维护责任。"""
    rows = []

        penalty = max(0, cost - cost_tolerance) * 1.5
        rows.append((gap + penalty, name, gap, penalty))
    return sorted(rows)

14.2 一个能跑起来的最小 Harness

用规则模拟「模型决策」，把 Harness 的五件事做全：工具注册、上下文组装与压缩、权限门、停止条件、trace 记录。运行后会看到完整执行轨迹。

# mini_harness.py —— python3 mini_harness.py
import json

class MiniHarness:
    def __init__(self, tools, allowed, max_steps=6, compact_after=4):
        self.tools, self.allowed = tools, set(allowed)
        self.max_steps, self.compact_after = max_steps, compact_after
        self.ctx, self.trace = [], []

    def _compact(self):
        if len(self.ctx) > self.compact_after:
            head = self.ctx[0]
            self.ctx = [head, {"role": "system", "text": f"[已压缩 {len(self.ctx)-2} 条历史]"}] + self.ctx[-1:]
            self.trace.append("COMPACT")

    def decide(self, goal):
        """规则版模型：没查过就查，查过没写就写，写完就停。"""
        done = {t["tool"] for t in self.trace if isinstance(t, dict)}
        if "search" not in done: return "search", {"q": goal}
        if "write" not in done:  return "write", {"path": "report.md", "text": goal}
        return "finish", {}

    def run(self, goal):
        self.ctx.append({"role": "user", "text": goal})
        for step in range(1, self.max_steps + 1):
            name, args = self.decide(goal)
            if name == "finish":
                self.trace.append({"step": step, "tool": "finish", "result": "done"})
                break
            if name not in self.allowed:                       # 权限门
                self.trace.append({"step": step, "tool": name, "result": "BLOCKED"})
                break
            result = self.tools[name](**args)                  # 执行工具
            self.ctx.append({"role": "tool", "text": json.dumps(result, ensure_ascii=False)})
            self.trace.append({"step": step, "tool": name, "result": result})
            self._compact()                                    # 上下文压缩
        return {"steps": len(self.trace), "context": self.ctx, "trace": self.trace}

TOOLS = {
    "search": lambda q: {"hits": 3, "query": q},
    "write":  lambda path, text: {"path": path, "bytes": len(text)},
}
if __name__ == "__main__":
    h = MiniHarness(TOOLS, allowed=["search"], max_steps=6, compact_after=2)
    print("—— 只放行 search ——")
    print(json.dumps(h.run("调研 Harness 选型"), ensure_ascii=False, indent=2))
    h2 = MiniHarness(TOOLS, allowed=["search", "write"], max_steps=6, compact_after=2)
    print("—— 放行 search + write ——")
    print(json.dumps(h2.run("调研 Harness 选型"), ensure_ascii=False, indent=2))
实测结论：只放行 search 时，Agent 在第 2 步被权限门 BLOCKED，循环提前终止；放行两个工具后走完 search → write → finish，并在上下文超过阈值时触发 COMPACT。这正好复现了视频里「上下文越来越长怎么控制」「工具权限怎么管」两个追问的最小形态。

14.3 三档控制粒度：拦截 → 替换策略 → 替换核心

把第 12.1 节的 L1/L2/L3 写成一个内核，直观看出每多开一个控制点会发生什么。

# control_granularity.py —— python3 control_granularity.py
class Kernel:
    def __init__(self):
        self.hooks = {"PreToolUse": [], "PostToolUse": []}   # L1
        self.compactor = lambda ctx: ctx[-4:]                 # L2（可替换策略）
        self.loop = self.default_loop                         # L3（可替换核心）

    def provide(self, service, impl):
        if service == "agent-loop": self.loop = impl          # 对应 ctx.provide
        elif service == "compactor": self.compactor = impl

    def default_loop(self, tasks):
        return ["ACT " + t for t in tasks]

    def plan_then_act(self, tasks):
        return ["PLAN " + ",".join(tasks)] + ["ACT " + t for t in tasks]

    def call(self, tool, arg, ctx):
        for hook in self.hooks["PreToolUse"]:
            if hook(tool, arg) is False: return "BLOCKED"
        ctx.append(tool + ":" + arg)
        ctx = self.compactor(ctx)
        for hook in self.hooks["PostToolUse"]: hook(tool, arg)
        return ctx

if __name__ == "__main__":
    k = Kernel()
    k.hooks["PreToolUse"].append(lambda t, a: False if "rm" in a else True)
    print("L1 拦截:", k.call("bash", "rm -rf /", []))
    print("默认 Loop:", k.loop(["read", "write"]))
    k.provide("compactor", lambda c: ["[摘要]"] + c[-1:])     # L2
    print("L2 压缩:", k.call("read", "a.md", ["x:1", "y:2", "z:3", "w:4"]))
    k.provide("agent-loop", k.plan_then_act)                   # L3
    print("L3 换核:", k.loop(["read", "write"]))
实测输出：L1 拦截: BLOCKED；默认 Loop: ['ACT read', 'ACT write']；L2 压缩: ['[摘要]', 'read:a.md']；L3 换核: ['PLAN read,write', 'ACT read', 'ACT write']。三段分别对应 Claude Agent SDK 的 Hook、Deep Agents 的 Middleware、DeepSeek Harness 的服务注册。

14.4 三层次判定器：插件 / SDK / 源码改造

# three_levels.py —— python3 three_levels.py
def decide(*, own_product=False, custom_ui=False, own_users=False,
           change_loop=False, extension_enough=True):
    if change_loop:
        return ("③ 改造底层 Harness", "fork 源码 / 服务级替换 Loop", "高：自建回归评测")
    if own_product or custom_ui or own_users:
        return ("② 开发自己的 Agent 产品", "用 SDK 复用执行能力", "中：产品工程 + 版本适配")
    if not extension_enough:
        return ("② 或 ③（需先确认接口边界）", "优先确认 SDK 能否覆盖", "中～高")
    return ("① 扩展现有 Agent", "Extension / Skill / Plugin", "低：跟随上游升级")

CASES = [
    ("给公司 Pi CLI 加代码规范检查", dict()),
    ("做自有 AI 编程产品：界面 + 用户体系", dict(custom_ui=True, own_users=True)),
    ("重新设计模型决策与循环顺序", dict(change_loop=True)),

#误区为什么错正确做法
1Harness 是 LangGraph / Framework 的新版本，用了它就该全换掉三层是不同抽象层次，上层复用下层；生产系统常同时用Framework 编排大流程，Runtime 管状态与恢复，Agent 在 Harness 内执行
2所有 Agent 开发都应该上 Harness视频明确限定：简单任务 / 严格流程场景，Framework 与 Runtime 依然有价值先看流程是否可枚举，再决定起点
3按「功能数量」选型工具调用、上下文管理、多 Agent 已是通用能力，不是差异点看「默认实现了什么机制」×「开放了多少控制权」
4控制权越高越好能改的越多，设计 / 调试 / 维护责任越大取满足需求的最低控制粒度（第 12.1 节 L0–L4）
5把 OpenClaw / Hermes 与 Claude Agent SDK 放在同一根轴上比前者是「完整 Agent 系统 = Harness + 消息接入 + 任务调度」，差异来自场景外壳先判断要不要场景外壳，再在同一场景内比控制粒度
6开发自己的 Agent 产品 = 要开发自己的 Harness视频结尾特意划了不等号；产品外壳与执行系统是两层用 SDK 复用执行能力，把精力放在界面 / 用户 / 业务
7为了加一个小功能直接 fork 源码把层次 ① 的问题做成层次 ③，长期承担合并成本先确认 Hook / Extension / SDK 是否够用
8靠堆 Hook 就能改变 Agent Loop 的决策顺序拦截点分散，逻辑隐式、难调试、难回归确实要改决策顺序时，进入服务级替换（L3）
9「可定制」等于「开箱可用」Deep Agents 灵活但执行环境、策略组合、沙箱与否都要自己定把技术决策列成清单并逐项确认责任人与验收方式
10自学习 / Skill 沉淀一定越用越好错误经验也会被沉淀并反复复用（视频明确点出）记忆与技能修改加人工审批，并保留回归评测
11改了默认机制，看成功率没变就算没退步Loop 改动常表现为步骤数、重试、工具误用率漂移，成功率可能不变同时看 Outcome 与 Trace，配护栏指标
12SDK 自带权限就等于生产安全权限白名单、审批与沙箱是三件事；client-server 架构还有额外攻击面最小权限 + 人工审批 + 隔离沙箱 + 命令审计

开篇与三层抽象（00:00–05:11）

如果今天让你开发一个 Agent 第一步应该做什么，直接写代码？错，要先选一个适合你的开源基础框架。现在市面上的 Agent 的开发框架越来越多，从 LangGraph 到 Claude Agent SDK、Deep Agents，还有 Pi、DeepSeek Harness，这些项目到底有什么区别应该怎么选？这期视频我们就系统地梳理了 Agent 的开发框架的演进过程，重点对比七个比较有代表性的项目。

分析它们各自的基础特点、优势和限制，最后再讲一个非常实际的问题：如果我们今天真的要开发一个 Agent，到底应该怎么使用这些框架。那内容比较长，大家可以根据章节直接调到感兴趣的部分。在开始具体选型之前，我们先来看一下 Agent 开发架构的演进。

大体上可以分成三个阶段，从早期的 Agent Framework，到后来的 Agent Runtime，再到现在越来越成熟的 Agent Harness。第一阶段是 Agent Framework，大概在 2022 年、2023 年，随着大语言模型流行起来，大家就开始尝试基于大模型开发各种应用，但那个时候开发 Agent 的很多基础工作。

都要自己完成，比如说怎么调不同的大模型、怎么让模型使用外部的工具，怎么接入知识库，怎么把工具执行的结果返回给模型，让它决定下一步做什么。那如果每开发一个 Agent，都要把这些功能重写一遍，开发成本就太高了。

所以就出现了 LangChain、LlamaIndex 这样的开发框架。那它们把模型的调用、工具的接入、数据的处理，以及构建 Agent 的一些基础能力封装起来，那开发者不需要每次都从零开始。比如说我们要开发一个订单查询的 Agent，可以先在 LangChain 里面去定义一个 Agent。给它接入订单查询的接口，再配置好提示词和调用的规则，很快就能搭出一个基础版本。

LangChain、LlamaIndex、CrewAI，都属于这一类的 Framework。它们主要解决的是减少重复开发，让 Agent 更容易构建。那第二阶段是 Agent 的 Runtime，随着 Agent 的执行任务越来越复杂，大家发现：仅仅把模型和工具连接起来还不够。比如我们要开发一个电商选品的 Agent，要先读取商品的信息，

然后查询库存、价格、佣金。接着给商品打分，最后再生成选品的结果。这里面的步骤很多，有些必须要按照固定的顺序执行。有些则需要根据上一步的结果决定接下来该怎么做如果任务执行到一半失败了，能不能接着之前的进度继续？

如果某个环节需要人工确认，能不能先暂停，等用户确认之后再往下走。这些已经不只是模型调用和工具接入的事情了，我们还需要管理整个任务的执行流程。保存执行的状态，处理中断和恢复。于是在 2024 年，LangChain 团队推出了 LangGraph，它的核心就是让开发者能够更聪明地，控制 Agent 的执行过程，比如任务有哪些步骤，步骤之间怎么流转。

什么时候暂停，以及出现了异常怎么恢复。Runtime 解决的是，怎么让 Agent 的执行过程可管理、可恢复。第三个阶段是 Agent Harness，随着模型的推理能力、工具调用能力不断提高，Agent 的开发方式又发生了变化。以前开发一个复杂的 Agent，开发者往往需要提前把很多执行流程安排好。

但现实中有些任务的流程，根本没有办法提前规划。也不可能枚举所有的情况。所以我们开始希望只给模型一个目标，让它自己去规划步骤。调用工具、分析结果，再不断地调整下一步的行动。比如让 Agent 帮我们研究一家公司的产品。

那模型可以自己决定先搜什么样的资料，哪些信息需要进一步验证。要不要写一段代码分析数据。最后怎么整理成报告，这些步骤，不一定需要开发者提前全部规定好。但是模型的自主性提高之后，又带来了新的工程问题。比如说 Agent 的连续执行几十步，积累了大量的上下文。

怎么避免它越来越长，任务执行的过程中文件和中间结果放在哪里。什么时候应该调用子 Agent，什么时候应该停止。怎么管理工具的权限，这些问题逐渐变成了 Agent 开发的重点。Agent Harness 因此受到越来越多的关注。那 harness 可以理解成，围绕着模型的一整套执行的系统。

它包含基础的 Agent Loop，也就是模型的思考、调用工具拿到结果、继续执行这个循环，在此之上还提供了上下文的管理、任务规划、文件系统、工具权限等能力，过去这些能力都得自己手写。现在成熟的 harness 已经帮我们做好了，我们可以直接使用这套现成的执行系统。再根据业务需求去扩展。当然 Framework、Runtime、Harness。

并不是简单的新技术取代旧技术，实际上 harness 本身就复用了 Framework 和 Runtime 的能力。LangChain 团队就是一个非常典型的例子，2022 年推出了 LangChain，主要提供 Agent 开发的技术组件。2024年推出了 LangGraph，补充了状态管理和持久化的执行能力。

2025年又推出了 Deep Agents，在前两者的基础上提供一套更加完整的 Agent Harness。今天的 Deep Agents 仍然是建立在 LangChain 和 LangGraph 之上的，所以这三个阶段并不是互相淘汰的关系，而是随着模型能力和应用需求的发展，出现的不同层次的技术抽象。这条技术演进路线影响的是什么呢，影响的就是 Agent 的开发的起点。

过去我们可能要从模型工具这些技术组件开始，一点一点去组装一个 Agent。现在如果现成的 harness 的执行机制能满足需求，就可以直接复用，不用再从零搭建。那起点变得更高了。不过你的业务如果足够简单，或者需要严格的执行流程状态管理，那 Framework 和 Runtime 依然有价值，依然可以用，并不是所有的 Agent 的开发都需要用到 harness。

讲完技术的演进，我们再来看看目前有哪些值得关注的 harness。按照主要服务的场景。

代表项目（上）（05:11–10:23）

我把它们分成了三类：第一类是综合任务类的，代表的项目就是 Claude Agent SDK 和 Deep Agents。这类 harness 不局限于某一种业务，可以用于研究、数据分析、文档处理、代码执行等复杂的任务。第二类是编码类的，代表的项目是 Pi 和 OpenCode。另外还有 Codex CLI，这类 harness 最初是围绕着软件开发设计的，重点支持代码的理解、文件的修改、

执行命令以及测试验证。第三类是个人助手类的，代表的项目是 OpenClaw 和 Hermes Agent。这类 Agent 系统更关注长期的记忆、多渠道的交互、定时任务，以及持续地为用户提供服务。除此之外还有一个非常特别的存在，是 DeepSeek Harness。

它的特点不是针对于哪种具体的场景，而是在于整个 harness 采用了高度插件化的设计，你可以通过组合不同的模块，把它搭成不同类型的 Agent，需要说明的是，上面的分类并不是严格的功能边界。实际上综合任务类和编码类的 harness 的能力，已经越来越接近了。一个 coding Agent 同样也可以去搜索资料，读取文件处理数据生成报告。

而一个通用 Agent 也可以去读写代码执行命令，它们的主要区别在于，默认提供了哪些工具、针对什么任务做了优化。另外 OpenClaw Harness 也不只是 harness，而是一套完整的 Agent 系统。包含了 harness、消息接入、任务调度等能力，下面我们就按这几个类别，看看每个项目最有特点的设计是什么，以及它们分别适合什么样的开发需求。

首先是综合任务类的，典型的代表是 Claude Agent SDK 和 Deep Agents。这两个项目都已经提供了比较完整的 harness 能力。但设计思路明显不同，先看 Claude Agent SDK。Claude Agent SDK 的本质是把 Claude Code 的 harness，封装成了一套可以直接使用的执行系统。它已经替开发者做好了 Agent Loop、工具的发现与调用、

权限和上下文管理，以及子 Agent 的执行机制。你只需要通过 hook，自定义的工具 Skills 和子 Agent 的定义来改变它的行为，但是不能把底层的核心实现直接替换成另一套机制。比如说通过 hook，你可以在工具调用前去检查参数、阻止执行，也可以在执行后去检查结果，还可以自定义系统的提示词，决定往上下文里补充哪些信息，工具方面，它已经内置了文件操作等基础工具。

区别在于 coding Agent，是围绕着软件开发场景设计的，所以会更重视代码的搜索文件的修改。命令的执行和测试验证。首先是 Pi，Pi 最大的特点是极简，尽可能地减少框架预置的功能，把更多的设计留给了开发者。它内置了基础的 Agent Loop。

但是默认只有四个工具：读取文件、写入文件、编辑文件和执行命令。那像任务的规划多 Agent 的协作这样的能力，Pi 并没有强制去内置一套固定的方案。而是允许开发者通过 extension 自己扩展。而且 Pi 的扩展机制也很开放，不只能增加工具，还能深入干预执行过程。比如说拦截工具的调用、修改上下文、替换压缩策略。

你希望自己掌握 Agent 的执行逻辑，从一个轻量的核心出发。开发自己 Agent 的产品。那接下来是 OpenCode。如果说 Pi 追求的是极简，让开发者自己决定做什么扩展。那 OpenCode 的思路就是提供一套比较完整的，软件开发工作机制。

它不仅内置了 Agent Loop，还预置了不同的 Agent 的角色和执行方式。比如说 Build Agent 负责实际开发，可以修改代码执行命令。Plan Agent 主要负责分析问题、制定方案，默认不直接修改普通项目文件。还有 Explore 等子 Agent 用于搜索和理解代码库。也就是说 OpenCode 已经帮开发者设计好了，一整套软件开发的工作方式。
