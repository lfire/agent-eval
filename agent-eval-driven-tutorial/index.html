2. 引言：评测必须从产品设计时介入

视频原述「很多 Agent 看起来很惊艳，但真正要看的是谁能在生产环境里稳定完成。这既考验 harness 的设计，也考验团队能不能判断每次改动是进步还是退步。而这里经常被忽视的一环就是评测。」

视频原述「演示惊艳、评测缺位，Agent 的迭代就变成猜。评测应该从产品设计时就介入，成为决定改什么、怎么改、能不能上线的关键依据。」

图 2｜开场封面「演示惊艳 → 评测 → 生产环境 → 稳定完成」重绘

开场封面把问题画成一条生产流水线：左端是「演示惊艳」的输入，中间是拿着放大镜的「评测」，右端是「生产环境」的齿轮与「稳定完成」的产出；红色的失败标注散落在链路上——工具不稳、上下文丢失、修好又出错、任务失败。没有放大镜，这些失败只会在用户那里暴露。

视频原述紧接着画面依次切到两篇参考文章：Anthropic 那篇给出「怎么定义评测、怎么组织组件」，阿里技术那篇《AI Agent 应用精细化评测：评测体系设计与工程实践》「又给出了具体的工程落地思路」。主讲人还在 00:51 提前亮出了自己整理的《Agent Eval 指标地图》，并说明「大家可以按照时间轴看，想反复阅读的也可以找我要文字版」。

补充为什么「演示惊艳」不等于「生产可用」：Anthropic 把这种状态称为 reactive loop（反应式循环）——只在生产环境里等问题冒出来，修一个故障又制造另一个；没有评测时，团队无法区分「真实退化」与「随机噪声」，也无法在发布前把改动跑过上百个场景。评测的价值是复利的：成本在前期一次性可见，收益却随 Agent 生命周期持续累积，包括免费获得 baseline 与回归测试（延迟、Token、单任务成本、错误率），以及成为产品团队与研究团队之间带宽最高的沟通渠道。
补充评测驱动开发（eval-driven development）：先写评测来定义「计划中的能力」，再迭代 Agent 直到它表现良好。这与「先做 Demo 再补评测」的顺序正好相反；好处是新模型发布时，跑一遍套件就能立刻知道哪些「押注」兑现了。Anthropic 建议把定义评测任务当作检验「产品需求是否足够具体」的压力测试。

3. Agent 的错误发生在执行链路上

视频原述「传统的评测只围绕最终的回答展开——相关性怎么样、答案对不对。但 Agent 接到任务要先理解需求、再调用工具读取结果、有时还要重试、调整计划，最后才生成答案。这条链路上的任何一个地方错了，后面的工具调用再顺利，也是给错误的订单退款，退的金额也是错的。」

图 3｜01:06「订单选错 → 工具调用 → 退错订单」执行链路与「检查完整执行」重绘

视频原述「所以评测要覆盖一次完整的任务执行：不只看它说了什么，还要看最后系统变成了什么状态。而这些步骤又是连在一起的——你改了提示词、为了让它记住更多信息，那其他的任务有没有受影响？靠感觉是看不出来的。评测的作用是让问题尽量在用户之前暴露出来。」

对比只评最终回答（传统）覆盖完整执行（Agent 评测）
观察对象output：模型生成的文本outcome + transcript / trace：环境终态 + 全过程记录
典型漏判答案措辞漂亮，但订单选错、金额退错逐节点校验：订单正确 / 金额正确 / 状态成功
改动影响无法判断改提示词是否拖累别的任务回归集持续跑，发现跨任务退化
失败归因只知道「不对」，不知道哪里不对定位到感知 / 规划 / 记忆 / 工具某一环节
补充output ≠ outcome（Anthropic 明确区分）：一个订票 Agent 在 transcript 末尾说「您的机票已预订」，但 outcome 是「环境的 SQL 数据库里是否真的存在这条预订记录」。同一篇里还举了 Opus 4.5 在 𝜏2-bench 订票题中发现政策漏洞的例子：按静态评测它「失败」了，实际却给了用户更好的解法——这提醒评测设计要给创造性解法留余地，不要死守固定路径。

4.1 Outcome：事情到底做成没有

视频原述「Anthropic 专门区分了 output 和 outcome。比如说一个 Agent 最后告诉你『退款成功』，真正要去系统里面看：订单对不对、金额对不对、状态是不是已经变成了成功。所以任务完成率是整个评测体系的北极星指标——不管 Agent 内部多复杂，事情到底有没有办成。」

视频 02:24 的画面是一张「退款成功」单据被放大镜逐项核对：订单正确 ✓ / 金额正确 ✓ / 状态成功 ✓，旁边橙色标注「核验真实结果」。

补充阿里文章对任务完成率的判定口径是「语义层面的完成度」：不要求字面匹配，但核心信息不能缺失；用户问「商品为什么不可售」，只要正确输出了不可售原因的诊断分析即通过。幻觉率（忠实性）的边界也值得记住：只判断 Agent 有没有「忠实转述」它看到的检索片段与工具返回值，不判断信息源本身对不对；凭空捏造接口名、函数名、配置项，或给出与检索结果直接矛盾的核心信息，才判幻觉。

4.2 Trace：过程有没有问题

视频原述「Trace 可以理解成 Agent 的行车记录仪：它调用了什么工具、工具返回了什么、中间走了几步。两条链路都通过了、最终都退款完成，但一条一次完成，另一条反复重试了好几次——只看结果，你看不出体验的差别，也看不出问题到底出在哪。」

图 5｜02:57「Trace 行车记录仪」与感知→规划→记忆→工具链路重绘

视频原述「阿里这篇实践文章在 Trace 层做了非常详细的拆解，按感知、规划、记忆、工具四块：感知解决的是『看懂了没』（用户要退款还是要查询），规划解决的是『想对了没』（该走 Skills、知识库还是工具），记忆解决的是『记住了没』（前面已确认的信息还记不记得），工具解决的是『做对了没』（工具有没有选对、调用有没有成功）。」

视频原述「评测体系要和你的 Agent 架构同构。评测就要沿着这条链路去拆，这样一个指标下降的时候，你能知道是该改提示词、还是改工具描述，而不是只拿到一个总分。」

补充阿里文章把「同构」写成了三条设计原则：评测面向架构（按感知/规划/记忆/工具逐层拆解，每层质量独立可观测）、指标面向行动（每项指标是一份诊断报告而非成绩单，下降时能直接告诉你要改 Skills、换 MCP 工具还是优化检索）、能力面向产品（评测是像监控告警一样可持续运行、可横向对比、可追溯演进的基础设施）。文章用了一个比喻：端到端评测像把车开上测试跑道，只回答「能不能从 A 到 B」；模块级评测像把车架上升降台，看发动机、刹车、油路各自状态，提供「把车修好」的路径。

4.3 Experience：体验和成本

视频原述「任务完成了，但调用过多、让用户干等半分钟，或者一个简单问题烧掉了大量 Token，都不能叫好用。所以还要增加成本和性能两个维度：比如模型调用次数、工具调用次数、Token 消耗、首 Token 延迟、端到端延迟。」

视频 04:03 的画面是「Token 账单（老板扛不住）」+「等待太久（用户等不起）」+「调用过多」，标题写着 Experience 体验和成本。视频把它总结成：结果质量、过程质量、体验与运行成本三方面放在一起，才能说清楚你到底想把 Agent 优化成什么样——这是后面整套评测的基础。

补充阿里文章把三维度写成「质量 × 成本 × 性能」：质量维度（答案是否正确、完整、忠实、有无幻觉）是底线但不是全部；成本维度（模型调用次数、工具调用轮次、Token）；性能维度（首 Token 延迟 TTFT、端到端延迟、模块级延迟）。「回答正确但耗时 30 秒」或「每次消耗 10 万 Token」都不可持续，健康的 Agent 是三者在当前业务场景下的最优平衡。

6. 任务收集：从哪来、怎么标

视频原述「别一上来就用表达准确的『标准题』去测 Agent——真实用户那里省略、指代、临时改主意全都来了，你都接不住。可以从手工测试、真实的日志、用户反馈或者线上失败里面，找 20–50 条有代表性的任务先跑起来。后面如果要识别更小的差异，再逐步扩充。」

补充这正是 Anthropic 的 Step 0「Start early」：团队常因为「以为需要几百条任务」而迟迟不动手，其实早期每次改动的效果量很大，小样本就够；等 Agent 成熟后才需要更大更难的评测集来分辨细小差异。原文原话是「最好一开始采用 80/20 法则」「评测越晚建越难建」。

9. 评测的稳定性：算出来的分靠谱吗？

视频原述「CHAPTER 07：算出来分靠谱吗？这是 Agent 测试和传统软件测试非常不同的地方——概率指标。同一个任务第一次跑可能成功、第二次失败、第三次又成功，你会认为它 100% 没问题吗？当然不是。重要的 case 要重复执行。」

图 13｜11:06「pass@k / pass^k，k=3」概率指标重绘

视频原述「Anthropic 在这里讲了两个指标，k 可以简单取 3：一个指标看它到底有没有至少一次成功，下一个指标则要求连续 case 都成功。对于真正面向用户的 Agent，后者更重要——因为用户每次来都希望事情办成。」

指标定义（Anthropic 原文）随 k 增大适用场景
pass@kk 次尝试中至少有一次得到正确解的概率。pass@1 = 50% 表示模型第一次就成功解决了一半任务上升：射门次数越多，至少进一球的概率越高只要有一个可行解就够的工具（如 coding 里提出多个方案）；也常被用来衡量能力上限
pass^k全部 k 次 trial 都成功的概率。单次成功率 75%、k=3 时 0.75³ ≈ 42%下降：要求次次一致，门槛更高面向用户的 Agent：用户每次来都期望事情办成
两者在 k=1 时完全相同（都等于单次成功率）；到 k=10 时会讲出截然相反的故事：pass@k 趋近 100%，pass^k 掉到 0%。选哪个取决于产品要求，而不是哪个数字好看。
补充阿里文章虽未直接写 pass^k，但在执行引擎里做了配套设计：E2E_MOCK 模式注入确定性的工具返回值，消除外部依赖抖动、保证结果可复现；E2E_REAL 保留真实链路。多轮对话场景每组生成独立 sessionId、轮次间等待约 2 秒持久化完成、成本指标逐轮累加、所有轮次输出拼接后统一评判。这些都是为了让「重复执行」真的可比。

16.1 pass@k 与 pass^k（复现原文 42%）

import random

def pass_at_k(p, k):        # k 次里至少一次成功
    return 1 - (1 - p) ** k

def pass_power_k(p, k):     # k 次全部成功
    return p ** k

p, k = 0.75, 3
print("pass@3 =", round(pass_at_k(p, k), 6))       # 0.984375
print("pass^3 =", round(pass_power_k(p, k), 6))    # 0.421875 ≈ 42%

# 蒙特卡洛校验（10 万次实验）
N = 100_000
at_least_one = sum(any(random.random() < p for _ in range(k)) for _ in range(N)) / N
all_success = sum(all(random.random() < p for _ in range(k)) for _ in range(N)) / N
print("sim pass@3 =", round(at_least_one, 4), " sim pass^3 =", round(all_success, 4))

# k 增大时两者讲相反的故事
for k in (1, 3, 10):
    print(f"k={k:2d}  pass@k={pass_at_k(p,k):.4f}  pass^k={pass_power_k(p,k):.4f}")
运行结果：pass^1 = pass@1 = 0.75，pass@3 ≈ 0.984 而 pass^3 ≈ 0.422；到 k=10，pass@10 ≈ 0.9999 而 pass^10 ≈ 0.056。这正是视频强调「重要 case 要重复执行」的数学原因。

def judge_case(case, mode):
    """返回 (verdict, reason)。主指标定通过，护栏一票否决，上游错误跳过下游。"""
    if case.get("route_expected") == "SKILL_MISS" and case.get("route_actual") == "SKILL_HIT":
        # 路由误触发：RAG 未执行，下游 Judge 标记 error 并跳过统计
        return "ERROR", "route_mismatch: downstream RAG judges skipped"
    if case.get("unauthorized_action"):
        return "FAIL", "guardrail: unauthorized action (高分不能抵消)"
    key = MAIN_METRIC[mode]
    return ("PASS" if case["scores"].get(key, 0) == 1 else "FAIL"), f"main={key}"

cases = []
for i in range(100):
    cases.append({
        "id": f"KQA-{i:03d}",
        "route_expected": "SKILL_MISS",
        "route_actual": "SKILL_MISS" if i < 10 else "SKILL_HIT",  # 只有 10 条真正执行
        "unauthorized_action": False,
        "scores": {"task_completion": 1, "instruction_following": 0,  # 格式没过，但不影响通过
                   "faithfulness": 1},
    })
verdicts = [judge_case(c, "END_TO_END") for c in cases]
passed   = sum(v == "PASS" for v, _ in verdicts)
failed   = sum(v == "FAIL" for v, _ in verdicts)
skipped  = sum(v == "ERROR" for v, _ in verdicts)
denominator = passed + failed          # error 既不进分子也不进分母
print(f"总数 100 ｜ 已执行 {passed+failed} ｜ 未执行(error) {skipped}")
print("通过率 =", passed, "/", denominator, "=", passed / denominator)
print("护栏/跳过示例：", judge_case({"unauthorized_action": True,
      "scores": {"task_completion": 1}}, "END_TO_END"))

16.6 最小评测 Harness（并发 + 隔离 + 汇总）

from concurrent.futures import ThreadPoolExecutor

def run_trial(task, agent, env_factory):
    env = env_factory()              # 每个 trial 从干净环境开始（Step 4）
    trace, outcome = agent(task["input"], env)
    scores = {g["name"]: g["fn"](trace, outcome) for g in task["graders"]}
    return {"task": task["id"], "trace": trace, "outcome": outcome, "scores": scores}

def run_suite(suite, agent, env_factory, trials=3, workers=3):
    jobs = [(t, k) for t in suite for k in range(trials)]
    with ThreadPoolExecutor(max_workers=workers) as pool:
        results = list(pool.map(lambda j: run_trial(j[0], agent, env_factory), jobs))
    by_task = {}
    for r in results:
        by_task.setdefault(r["task"], []).append(r)
    # pass^k：每个 task 的所有 trial 都必须全 grader 通过
    def ok(r): return all(v == 1 for v in r["scores"].values())
    per_task = {tid: all(ok(r) for r in rs) for tid, rs in by_task.items()}
    return {"pass_pow_k": sum(per_task.values()) / len(per_task),
            "pass_at_k": sum(any(ok(r) for r in rs) for rs in by_task.values()) / len(by_task),
            "per_task": per_task}
实践提醒：真实环境里 agent 与 env_factory 必须和线上尽量一致；共享状态（残留文件、缓存、git history、CPU 内存）会让多次 trial 不独立，从而使分数失真。Anthropic 举过一个真实例子：Claude 通过翻看前几次 trial 留下的 git history 获得了不公平优势。

#误区为什么错正确做法
1等 Agent 做完、上线后再补评测越晚越难逆向还原成功标准；改动效果量变小后需要更大样本Step 0 尽早开始，20–50 条真实失败任务

9评测集只有正例只测「该搜索」会把 Agent 训成什么都搜正反例平衡，测 undertriggering 与 overtriggering
10只测「标准题」真实用户充满省略、指代、临时改主意、口语化表达任务来自真实日志 / 工单 / 客服队列

引言（00:00–01:06）

很多 Agent 的看起来很惊艳。但是上线之后问题才开始暴露，任务失败，工具调用不稳定。上下文丢失，刚修好了一个 bad case。又引入了一个新的问题，Agent 之间真正拉开差距的，要看谁能在生产环境里持续稳定的完成任务。这既考验 Harness 的设计，也考验团队能不能判断。

每次修改到底有没有让产品变好，而这里经常被忽视的一环就是评测。评测却为 Agent 的迭代就很容易变成，评感觉改哪有忽视。所以评测必须从产品设计室就介入，成为决定产品改什么怎么改。能不能上线的关键依据，今年1月，S-S-ROPE 发布了一篇 Agent 的评测的文章。系统的讨论了 Agent 的评测应该怎么设计，最近阿里的技术团队也发布了一篇。

Agent 的评测体系设计与工程实践，又给出了具体的工程落地思路。那今天呢，我们就把这两篇放在一起。讲清楚 Agent 的评测到底应该怎么做，视频的最后，我也整理了一个评测的治疗地图。方便大家对照自己的产品使用，内容比较多，信息密度很大。大家可以按照时间轴切换到感兴趣的章节，想反复阅读的也可以找我要文字版。传统大模型的调用。

Agent 的错误发生位置（01:06–02:17）

输入提示词模型给出回答，以前很多的评测都是围绕着最终的回答展开。答案准备准确，有没有幻觉，先关性怎么样。语言质量怎么样，但 Agent 不一样。Agent 的街道任务要先理解需求，安排步骤，再调用工具读取结果。再决定下一步，有的时候还要改文件。

更新订单，情况部队再调整计划。所以 Agent 的错误，不是只发生在最后生生答案的那一刻。而是发生在整条执行面路上的任何一个地方。比如说退款，订单找错了，后面的工具调用再顺利。也是给错误的订单退款，金额传错了，接口返回成功。

退的金额也是错的，所以 Agent 的评测。必须是要覆盖一次完整的任务执行，他说了什么，做了什么。最后系统变成了什么状态，都得有一句，而这些步骤又是连在一起的。你为了修改工具，改了提示词，有可能会影响任务的路由。为了让他记住更多的信息，又可能增加干扰，眼前的几个任务变好了。

那其他的任务有没有受影响，靠感觉是看不出来的，评测要改变的。就是这个被动的局面，让问题尽量在用户之前暴露出来。不少团队做评测，上来就列准确率，召回率。换绝率，只标列了一大堆，到底怎么才算是上线标准。没人说得清，我把这两篇文章的思路。

评测的三个层次（02:17–04:35）

整理成了三个层次、Outcome、Trace。Experience，事情有没有做成，过程有没有问题。以及体验和成本能不能接受，先说 Outcome。事情能不能做成，Aslopic 专门区分了。Output 和 Outcome。

比如说一个 Agent 的最后告诉你，退还引荐成功了，这个是 Output。真正区系统里面看，确实成成了一笔退款记录。而且状态已经变成了成功，这才是 Outcome。所以对于 Agent 来说，不能只看他最后说了什么。还要看这个任务结束以后，真实的世界或者系统。

状态到底发生了什么。所以任务完成率，作为整个端道端评测的北极星指标。因为不管 Agent 的内部多复杂，站在用户的角度，第一个问题永远是。我的事情到底有没有办成，一个 Agent 的查对订单。完成校验，顺利退款，另一个连续调错工具。

重视了好几次，最后也成功了，只看结果两条都是通过。但是显然你还想知道。第二个问题到底出在哪。所以需要看第二层 Trace，Trace 可以理解成 Agent 的行车记录仪。在一次任务里，Agent 调用了什么工具。

传了什么参数、工具返回了什么、每一部花了多久。都要记录在 Trace 里面，而阿里的这篇时间文章。在 Trace 这一层，做了非常详细的拆解。他把这个过程拆成四个模块，感知规划记忆和工具。感知解决的是看懂了没，用户的意图到底有没有理解正确。

用户要退款，还是只想问退款的规则，规划解决的是想对了没。应该走 Scale 知识库，还是工具，知识路径有没有选对。那记忆解决的就是记住了没，多伦对话以后，前面已经确认的信息还记不记得。你没有选对参数有没有传对，调用有没有成功，这背后的底层原则就是评测体系。应该尽量和你的 Agent 的架构同购，你的 Agent 是怎么工作的，你的评测就要沿着这条链路去拆。

这样一个指标下降的时候，你才能知道到底是应该改提识词。还是改工具描述还是改记忆。最后看 Experience 体验和成本，一个简单的查询，你让用户干等半分钟。任务完成率再好，用户也不可能想用。一个简单的问题，来回调了几十次模型。

烧掉了大量的 Token。增加成本和性能两个维度。比如说模型的调用次数，输入输出的 Token。端道端的延时等等，结果质量过程质量。体验与运行成本，这三个方面放在一起才能说清楚。

你到底想把 Agent 的优化成什么样，这是后面整套评测的基础。明确了什么叫做好。

评测框架（04:35–05:28）

接下来是评测体系本身有什么构成，Astropic 给了三个层级的概念。一条可以重复执行的测试任务叫做 Task，它要写清楚输入出使条件和成功标准。做到什么才算完成，有哪些行为不能发生提前约定。把同一批任务按照业务或者是能力组织起来，就是评测级，比如说多轮对话一组。工具调用一组，也可以把退款取消订单。

转任功放在客服业务的 suit 下面。然后你需要一套系统，把任务发给 Agent。准备工具和环境，保存之前的记录调用评分器。在汇总结果，这就是 Evo 的 Harness 评测框架。Task 向一道题，suit 向一套试卷。

Harness 是出题以后的运行记录评分都组织起来，同一道题没抱歉叫 Trails。也就是一次试跑，每一次都有指自己的执行记录 Trace。一个任务可以有多个评分器进行打分。你用一堆条件齐全表达准区的问题去测 Agent。

任务收集（05:28–08:14）

它当然容易表现得很好。但真实用户一开口，省略指代临时改变主意全都来了。接不住，那早期不需要追求特别大的数据级。可以从手工测试真实的日制，用户反会或者线上失败里面。找20-50条有代表性的任务先跑起来。

那它们是核心理极限发现明显的变化，后面如果要识别更小的差异再增加规模。预计至少要覆盖这四个情况。第一类是核心任务，也就是这个 Agent 的最重要最高频。最能代表产品价值的任务。比如说一个搜索的 Agent。

那它的核心任务可能就是信息的检索，跨来源的总结复杂问题的拆解。一个数据 Agent 核心的任务就是查数，分析归因是什么图表？这些产品靠它吃饭的能力，必须有对应的测试。第二个是真实用户的任务，这类数据最好直接来自于真实的日质。真实的 query 只是用户的使用记录。

因为产品经理自己构造的问题，往往太标准表达完整。一图清晰，但真实的用户不会这么说。第三类是历史的 Bad Case，这类数据其实特别值钱。线上真正出过问题，被用户投诉过人工排查过的问题。要求好了都应该沉淀进品测计，否则一个空可能就会掉进去两次。

第四类就是编解 Case，你的信息不够，多一图长对话工具异常。知识库没有答案，都要主动覆盖，不能只等着线上预见。顾手机多了，还要能快速的挑出这次应该测打鞋。可以按照下面之八类基金打标，组织专项的评测，基础技能的评测。测的就是 Agent 最核心的技术能力。

比如说一个任务该不该命中，某个 skill 最终有没有完成。知识问答评测机，主要就是测 req 和知识库相关的能力。该查的收查了吗，检索内容对不对，找到了证据的材料没有。回答有没有乱编，多轮对话的评测机测的就是，Agent 在连续多轮交互里面。还能不能保持上下文，能不能理解指代，用户中途切换了话题之后。

还能不能接得住，异常输入的评测机测的就是，系统会不会被不正常的输入搞乱。空输入超长的文本，乱码特殊字符，或者是一些异常的请求。Agent 会不会崩掉，或者是胡乱回答，根据调用的评测机专门测工具。该不该调，调哪个参数对不对，失败后该怎么办都得测？多一图的评测机，用户已计划里同时有两三个需求。

Agent 能不能完全识别出来，而不是只处理其中一个。模糊一图的评测机，用户说的不清楚的时候，Agent 会不会正确的澄清。而不是自己脑补，来尝对话衰竭的评测机。看对话越来越长之后，Agent 的 Memory 到底从第几轮开始明显下降。真正创建用力的时候，有三个地方尤其容易出问题。

第一是数据机要来自真实任务，人工构造的数据，可以保证测试的覆盖度。但是要保留真实使用的复杂程度，全都是构造数据很容易测不出问题。第二是机要有正力，要有反力，你只奖励 Agent 的调用搜索工具。它可能学会的就是，遇到什么问题都搜索。所以该调的时候要测，不该调的时候能不能控制住也要测。

第三是测试用力要有规范，用力不能只有问题和参考答案。还得写出是状态，成功条件必要约束。每条用力要完整的标注了。

评分器（08:14–10:12）

评测链路所需要的所有信息，这样一个 Task 跑一次。就能同时判断，Outcome 和 Trace 里面的多个环节。怎么判断它到底有没有作对，考虑就是评分器，评分器如果判错了。比一次任务做错更麻烦。因为你会拿着错误的分数，继续把产品往错误的方向改。

SROPEX 是把评分方式分成了三种：代码评分，模型评分和人工评分。这三种：先用代码评分，工具参数对不对。退款记录的订单和金额对不对，状态是否成功，有没有超过约定的时间。用程序检查更便宜稳定。而且还可以重复执行，有些事情代码判断很难。

解释有没有回答到用户关心的问题点，是否一路重要的条件？有没有便利知识库和工具返回的信息。那这些语异的问题，都可以用模型来评分。也就是 LLM as a judge。但是大模型的评分，不是简单的把所有内容。

认给一个更强的模型，让它从零到一百打个分。有四个很重要的原则，第一个是单一指责。一个 prompt 只凭一个指标，判断任务有没有完成。就对照完成条件，判断中时度就检查。有没有脱离证据乱编，不要让一个模糊的总分。

把几个不同的问题混淆在一起，复杂任务可以拆开判断。第二是先推理后判断，每个 prompt 都要求大模型。先输出思维链的推理，再给出结论：这不仅提高了判断的准确性。也让评测结果具备的可解释性。第三是福利引导，每个 prompt 都要包含。

典型的通过和不通过的势力。最后一个是结构化输出，不要让大模型自由发挥写一篇评价。而是要让它按照严格的，这份格式输出明确的结构化结果。方便后面自动统计，人工评分规则负责专业判断和校准。人工特别适合两个场景，一个是高度专业，或者是高度主观的问题。

另外一个很重要的就是校准大模型。比如说定期抽一批 case，让领域专家和大模型同时判断。看看差在哪，如果模型经常和专家的结论相反。那就应该先修改评分标准，而不是拿错误的评分去优化 Agent。代码查的清早要用代码，予以判断交给模型。

专业判断和校准留给人工，三种方式各自负责合适的部分。评分才有依据。

评测结果的判断（10:13–11:03）

任务完成了，工具调用也正确，但是格式没有按照要求。响应速度也很慢，这算通过还是不通过。阿里在这里用了一个，我觉得非常实用的方法。就是给不同类型的评测设置主 Agent，端到端的评测，重点看任务完成率。工具专项评测，重点看工具的选择和调用是否正确？

每一次评测，先回答自己最关心的那个问题。其他的指标不一定决定，整个 case 是否通过？而是作为整段信息存在，在实际的产品里，我觉得还可以增加一层互拦指标。某些错误一旦发生，不管其他指标多搞。这条 case 都必须非要。

比如说安全，隐私，或者不可逆的风险操作。还有一个细节，上游的指标错了，下游该怎么办？比如说一个问题本来走 RAG。但是 Agent 的路由错了，直接走了 skill。那这次的 RAG 根本没有执行。

如果直接给，减缩质量打零分，肯定不合适。像这种情况，下游的评分直接跳过统计。避免上游的错误，把后面几个指标一起拓地。

评测的稳定性（11:04–11:55）

如果你算出来的评测分数是90分。那是不是就说明没问题了呢，这是 Agent 的评测和传统软件测试。非常不同的地方，Agent 是一个概率系统。同一个任务，第一次跑可能成功。第二次失败，第三次又成功了，如果你刚好测到那一次成功。

你会认为它100%没问题。但对于真实的用户来说，这显然不是一个稳定的产品。所以对于复杂多不准的 Agent 的任务，重要的 case 要重复执行。sropik 在这里用了两个指标来讨论这种波动，一个指标可以简单理解成。你给它 case 机会至少要成功一次，它更适合判断 Agent 的能力边界。

也就是它到底有没有能力把这件事做出来。那一个指标则要求连续 case 都成功。对于真正面向用户的 Agent，这个指标更重要，因为用户每次来都希望事情办成。如果测的效果连续 case 都成功了，这下是不是该起火了。还不行，你修好了一个东西。很可能同时改坏另一个东西。

能力评测和回归评测（11:55–12:26）

复杂任务进步了，简单任务却退步了。这也不能直接叫整体变好，这就需要同时做能力评测和回归评测。能力评测解决的是这个 Agent 还有什么不会，回归评测解决的是以前它会的东西。现在还会不会，换模型改提是此加斯基尔。以前正常的任务还是需要继续正常，当某一类能力评测的问题。

被 Agent 持续稳定的得益解决之后，它就可以毕业了，进入到回归测试的数据机。原来它是一道难题，等解决之后它就变成了一条底线。这样你的评测数据机其实是在不断演化的，后这张指标地图列出了。

指标地图（12:26–12:35）

结果过程体验成本，以及稳定性和回归这些方向，大家可以按照自己的业务和产品的阶段。有针对性的选择，如果你能听到这你肯定会想。

结语（12:35–13:05）

评测也太复杂了吧，我搞个 Agent 都没这么复杂。这不是一份所有团队都必须照着，执行的标准答案，而是一个思路框架。真正开始做 evo 的时候，反而建议从简单开始。调几个最核心的任务，写清楚初始条件和成功标准。从真实问题和历史的 bad case 里面整理几十条，先把结果测起来，关键任务多跑几次。

再抽查评分和执行记录，不是指标越多评测就越好。评测应该让团队敢于改，也知道什么时候该停。下一次准备上线，至少能拿出证据说清楚。哪里变好了哪里退步了，这个版本为什么值得反？
