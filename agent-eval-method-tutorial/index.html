2. 为什么 AI 圈不叫 Test，而叫 Evaluation

视频原述视频 ② 开场追问：做互联网产品时我们说单元测试、接口测试、回归测试、QA，为什么到 AI 产品大家都开始聊 evaluation、LLM Evals、Agent Evals？画面还贴出 Anthropic《Demystifying evals for AI agents》、LangChain、Braintrust、DeepEval、Langfuse 的搜索结果。

图 2｜从 Test 到 Evaluation 的根本原因重绘
答案不是换了个说法，而是面对的产品对象变了：传统软件是确定性逻辑，AI 产品是概率性推理。Test 验证「功能是不是正确」——支付成功没有、数据库更新没有，都有明确标准；Evaluation 要回答「他真的理解用户意图了吗、有没有被骗退款、用户到底满不满意」，这些问题没有唯一答案，只有好和不好。

视频原述口播里的例子很直接：用户说「我想退款」，Test 只能告诉你退款流程走没走通；产品经理真正关心的是意图理解、风险、满意度。于是 AI 产品从正确性的测试走向质量的评估。

4. Evaluation 的关键要素：Rubric 定义「什么叫好」

视频原述视频 ② 的第二个官方章节（摘要逐字）：「evaluation 的关键要素是 rubric，用于定义什么是好的回答，衡量质量而非正确性」。

图 5｜Rubric 的作用重绘

视频原述画面举例：用户说「今天工作好累」，有没有先共情、有没有否定用户情绪——这些不是明确的 yes or no，而是质量的好坏。所以不能写「回答要好」，要拆成专业度、幻觉率、共情等维度，并给每个维度定义 1–5 分标准，写清 5 分 / 3 分 / 1 分分别对应什么。

5. 最小可行评估 MVE：三件套 + 一个循环

视频原述第三个官方章节标题「构建最小可行评估」，画面写的是 构建 mve（最小可执行评估），下面一行 eval driven development，再下面三个词 dataset rubric run。

图 6｜MVE 三件套与 eval driven development 重绘
  1. Dataset：去线上捞 50 个真实用户对话，包括那些最容易翻车的边界场景。这 50 个 case 就是产品的基本盘。
  2. Rubric：不要只说「回答要好」，把「好」拆成专业度、幻觉率等维度，给每个维度定义 1–5 分标准。
  3. Run：每次模型升级、每次 prompt 修改、每次 memory 更新，都把这套评估全部跑一遍，通过得分看变化，而不是做一次性的 vibe check。

视频原述口播强调「你不需要写代码，但需要亲手去搭」。三者合起来就是 eval driven development：用评测驱动每一次改动，而不是改完再看感觉。

校正：官方章节摘要把最后一句写成「ever driven development」，为 ASR 误写；画面与上下文均为 eval driven development，本教程按画面取词。

② LLM-as-a-Judge 模型评分开放式任务用 Rubric 判断质量；维度要写清 5 分 / 3 分 / 1 分各对应什么存在模型偏见与评分漂移（见第 16 章）
③ Human Evaluation 人工评测真实体验与审美陪伴 Agent 的「被理解/被关心」、创作 Agent 的「有意思」，模型评不出来成本高、周期长

视频原述画面特别提醒：「每个维度都要给明确的评分锚点，不能只写『准确性高』——裁判模型看到『准确性高』和『准确性低』会给出很随意的分。」

# three_layers.py —— python3 three_layers.py
def success_rate(traces, success_def):
    """success_def 决定什么算成功：说完了 vs 真办成了。"""
    ok = sum(1 for t in traces if success_def(t))
    return ok / max(1, len(traces))

def ux_scores(traces):
    n = len(traces)
    return {
        "追问率": sum(1 for t in traces if t["followup"]) / n,
        "点赞率": sum(1 for t in traces if t["liked"]) / n,
        "放弃率": sum(1 for t in traces if t["abandoned"]) / n,
    }

def business(traces, baseline_handoff=0.40):
    handoff = sum(1 for t in traces if t["handoff"]) / len(traces)
    return {"转人工率": round(handoff, 3), "较基线下降": round(baseline_handoff - handoff, 3)}

if __name__ == "__main__":
    traces = [
        dict(replied=True, ticket_issued=(i % 3 != 0), followup=(i % 3 == 0),

             steps=3 + i % 28)
        for i in range(60)
    ]

FIELDS = ("input", "expected_result", "criteria", "difficulty")
TARGET = {"简单": 0.40, "中等": 0.40, "困难": 0.20}

def audit(cases):
    missing = [c["id"] for c in cases if any(not c.get(f) for f in FIELDS)]
    vague = [c["id"] for c in cases if "回答" in str(c.get("expected_result", ""))]
    dist = {}

        d = c.get("difficulty")
        dist[d] = dist.get(d, 0) + 1
    n = max(1, len(cases))
    drift = {k: round(dist.get(k, 0)/n - TARGET[k], 3) for k in TARGET}
    return missing, vague, drift, dist

    for k, (op, limit) in guardrails.items():
        v = current.get(k, 0)
        if (op == "<" and not v < limit) or (op == ">" and not v > limit):
            reasons.append(f"护栏未过 {k}: {v} {op} {limit}")
    cal = current.get("calibration_drift", 0)
    if cal > drift_tolerance:
        reasons.append(f"裁判评分漂移 {cal:.2f} > {drift_tolerance}")
    return ("GO" if not reasons else "HOLD"), reasons

#误区为什么错正确做法
1把 AI 产品当传统软件做 Test输出是概率性、语义性的，没有唯一正确答案用 Evaluation：Rubric + 场景集 + Judge + 质量分
2只写「回答要好」当评分标准裁判模型看到「准确性高/低」会随意给分拆维度并写清 5 分 / 3 分 / 1 分锚点
3把「成功」定义成「回复了用户」订票案例：95% 成功率但投诉不断定义到业务结果：「用户拿到了可出行的票」
4只看最终成功率30 步完成与 3 步完成是两个 Agent同时测执行质量、耗时、Token、轮数
5Dataset 全是简单题或全是难题分数无法反映真实业务难度分布按 40% / 40% / 20% 分层，与线上分布对齐
6Dataset 只建一次不更新「半年后就是废纸」建立线上失败 Case 反向回流机制
7只用 LLM Judge 一种判据规则能稳判的维度被模型化，开放式维度又缺锚点规则 / 模型 / 人工三者组合
8不固定裁判模型版本与参数评分漂移让跨版本比较失去意义固定版本参数 + 10%–20% 人工复评基线
9只测组件或只测 E2E只测组件看不到真实路径，只测 E2E 难定位组件级 → 任务级 → E2E 三层粒度
10用 LLM Judge 分数向老板汇报价值企业不会因为 95 分继续投资业务层看 ROI：转人工率、成本、成交率
11靠 vibe check 判断改动好坏随手看几个样例无法跨版本比较每次改动把 MVE 全量跑一遍
12把重复的工具调用都当失误可能是为确认信息一致性的设计查 Trajectory 里的纠错前后逻辑链

它还是有 Test 的，对吧，它比方说你的结构化输出，你的工具调用。这些都是一个估计于规则的一种调用，它还是有 Test，它是明确的，Evaluation 真正多出来的东西，其实只有一个，就是 Rubric。也就是什么叫好，你要定义一个好，就一个，譬如啊，一个情感陪伴的 Agent 用户说，今天工作好累。那什么叫正确答案，没有的，对吧。但是，什么叫好的回答，我们可以定义。

譬如有没有先共情，有没有说教，有没有否定用户情绪，有没有继续表达，这些就是 Rubric。它就不是答案，它不是明确的 yes or no，它是一个质量的好坏。所以我们 AI 产品或者 Agent 的产品，都在开始教 Evaluation。因为 Test 只能验证有没有作对，但 Evaluation 开始衡量的是有没有做好。这是完全不同的问题。

那作为产品经理，如何构建你的最小可行的评估呢，我觉得你不需要写代码的啊。但是我们需要亲手去搭这套系统的灵魂。第一个就是黄金数据集啊，据线上去捞50个真实的用户对话。包括那些最容易翻车的边界场景，这50个 case 就是你产品的基本盘了。那第二个就是你要定义 Rubric。

不要只说回答要好，要把这个好拆解成专业度、幻觉率、工具调用、准确率。给每个维度定义1到5分的标准。第三步，每次模型升级、每次 proud 修改、每次 memory 更新，都全部跑一遍，不要问我觉得怎么样。也不要去 拍脑袋，而是问，通过这个数据来看，通过得分来看，我到底有没有变好。这就是我们说的 eval-driven development。

最后说一句感慨，就是产品经理会电影 Rubric 会变成，越来越重要的核心竞争力。因为你都不能定义什么叫好，你怎么能让这个产品变得越来越好。
